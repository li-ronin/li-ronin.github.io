AI Coding：从可验证的规格到云电脑执行闭环

1. 先改变问题：不是“怎样让模型多写代码”

把 AI Coding 理解成“把需求交给模型，拿回代码”，会漏掉软件工程里最贵的部分：需求是否一致、修改是否受控、结果是否正确。模型能够输出一个看似完整的函数，却无法仅凭流畅程度证明它满足业务。更有效的目标是缩短“提出假设—得到证据—修正实现”的循环。代码只是循环中的一个产物，规格、测试、运行记录和差异同样重要。

下面使用一个教学案例：给性能日志增加 p95 统计。已有程序读取 CSV，每行包含一次耗时，单位为毫秒。用户说“输出平均值和 p95”。这还不是可实现且可验证的规格：空文件怎么处理？负数、NaN、无穷大允许吗？p95 用最近秩还是线性插值？是否先跨设备合并？如果这些问题不固定，即使两个实现都“合理”，结果也可能不一致。

2. SDD：把自然语言压成可执行的约束

SDD 通常指 Specification-Driven Development，即用明确规格牵引设计、任务、实现和验证。它不是某个工具的专利，也不是写一份很长的 Markdown 就自动正确。GitHub Spec Kit 是提供结构化流程与模板的一个实现；这里借鉴的是规格可追溯的思路，而非依赖某组命令。参考：Spec Kit 官方仓库。

本例先约定：输入是同一设备、同一用例的独立耗时；必须有限且非负；空输入报错，不伪造 0；p95 采用最近秩法，排序后取第 ceil(0.95n) 个样本；输出保留原单位。验收例子 [10,10,11,12,100] 的均值是 28.6，p95 是 100。若采用线性插值，可能得到另一数值；不是谁算术错误，而是指标定义不同。

规格 S1：拒绝空输入
规格 S2：拒绝负数、NaN、Infinity
规格 S3：p95 = sorted[ceil(0.95 * n) - 1]
规格 S4：输入序列不可被统计函数原地修改
规格 S5：错误必须返回非零状态，不生成成功报告

每条规格应能对应一项测试或人工检查。S4 很容易被忽视：原地排序可能破坏调用者用来分析时间顺序的数据。把这些约束写清楚，实际是在给 Agent 设置搜索空间：它可以自由选择实现，但不能自行重新定义正确性。

3. 把任务交给 Agent，而不是逐行遥控它

一个好的任务包包含目标、约束、相关文件、可运行命令和完成条件。例如让 Agent 先读统计模块和现有测试，再增加纯函数与 CLI 接线，最后运行指定回归。不要同时塞入整个仓库全部日志；也不要只说“帮我优化”。前者让关键条件淹没，后者迫使模型猜测。

更接近 Agent Native 的工作方式，是让环境成为可反复操作的接口：一条命令创建隔离工作目录，一条命令执行测试，一份机器可读报告说明通过、失败、未执行。人提供不可擅自改变的验收条件，Agent 自行调查和迭代。这样从每一步都由人发提示，变成对可观察阶段负责。自主性增加的是执行选择，不是改变目标或发布权限的自由。

输入：S1—S5、相关模块路径、测试命令
输出：代码差异、测试结果、失败案例、未验证事项
边界：不改CSV格式；不删除失败测试；不自动发布
完成：新例子与旧回归都通过，报告绑定当前提交

任务拆分也要依据依赖：确定 p95 定义之后才能写预期值；修改函数与编写独立测试可以部分并行；发布必须等待验证。多个 Agent 各写一个相互冲突的“正确标准”，只会把猜测并行放大。

4. 看一小段实现，理解测试为什么必须独立

下面是核心算法片段，不包含 CLI、CSV 解析和错误码处理。输入验证后复制并排序，索引必须从数学中的第 1 项转换成程序中的第 0 项。测试者应从规格手算预期值，而不是把同一算法复制到测试中。否则实现把 ceil 写成 floor，测试也同样写错，两者会一起通过。

double p95(std::vector<double> samples) {
    if (samples.empty()) throw std::invalid_argument("empty");
    for (double x : samples)
        if (!std::isfinite(x) || x < 0)
            throw std::invalid_argument("invalid duration");
    std::sort(samples.begin(), samples.end());
    const auto rank = static_cast<std::size_t>(
        std::ceil(0.95L * samples.size()));
    return samples[rank - 1];
}

除了固定例子，还应验证性质：打乱输入顺序后结果不变；所有元素都加同一个正数，结果也增加该数；同一组样本乘以正数，结果按同一比例缩放。这些性质不能替代边界例子，却能暴露更广的错误。大规模输入还要考虑索引计算的数值边界、复制成本以及是否允许近似分位数，本例只讨论内存可容纳的精确统计。

5. AI 最容易漏掉的，不是代码，而是证据闭环

实现后至少检查三层：函数级测试回答算法是否正确；CLI 集成测试回答参数、文件和退出状态是否正确；真实格式样本回答现有工作流是否仍能使用。编译成功不是测试通过，测试通过也不是所有场景都验证过。报告必须写明哪些阶段运行了、哪些因环境限制未运行。

性能测试还要防止“更快但算错”。先验证数值，再固定输入规模、编译配置和硬件环境，预热后重复测量。让 AI 生成脚本时，要求同时保留样本、统计口径和失败退出码。Google Benchmark 提供迭代、重复测量等机制，但工具本身不会替你决定实验是否公平。参考：Google Benchmark 使用指南。

常见失败路径是：Agent 改了代码，之前的测试结果仍在目录里，于是报告拿旧的绿色结果当本次证据。解决办法不是提醒它“仔细一点”，而是让报告包含代码提交、输入摘要、命令和运行标识。验证产物必须绑定被验证对象；后续再改一行相关代码，受影响的检查就要重跑。

6. Computer Use：把UI当作带延迟和不确定性的环境

代码工具通常给出结构化状态，Computer Use 则需要从截图观察界面，再产生点击、输入或滚动动作。模型负责提出动作；宿主执行器负责实际操作；云电脑提供远端桌面和隔离环境。动作后再观察，形成闭环。Anthropic 的公开工具文档明确由应用在自己的环境中执行客户端工具调用，而不是模型直接变成操作系统的一部分。参考：Computer Use 工具文档。

以截图缩放为例：真实桌面 1600×900，发送给模型的是等比例缩小的 800×450 截图；若坐标原点相同，模型给出的 (620,240) 对应桌面 (1240,480)。若截图只是窗口裁剪，还要加窗口偏移。缩放、裁剪、浏览器缩放和滚动位置是不同因素，不能简单“乘二”解决所有场景。

更重要的是观察有效期：模型看到“保存”按钮后，页面可能弹出对话框。把旧坐标直接应用到新画面，会点到另一个控件。以下是教学状态机，不是某产品协议：

observation = capture()
action = model.decide(observation, goal)
validate(action, allowed_actions)
if environment_changed_since(observation):
    capture_again()
else:
    execute(action)
    new_state = capture()
    verify_business_result(new_state)

environment_changed_since 在真实系统里可能只能近似检测，因此仍需要执行后的验证。输入成功不等于保存成功，点击成功不等于表单提交成功。对于有副作用的操作，网络超时不能直接重试；先查询目标记录是否已生成，否则可能重复提交。

7. 工具选择、安全与团队框架的边界

有可靠 API 或 CLI 时，优先使用它们完成结构化操作；需要真实界面行为、没有接口或要做视觉验收时，再用 Computer Use。它们不是互斥阵营。一个任务可通过 CLI 跑测试，再用浏览器验证用户页面，但必须说明两种证据分别覆盖了什么。

云电脑不天然等于安全沙箱。应限制能访问的文件、网络和凭据，区分观察、编辑与发布能力。网页里的文字是任务数据，不能因为它声称“忽略此前要求”就获得新的权限。高风险动作需要独立校验，不能只靠模型自觉。多租户系统还要防止不同用户共享桌面状态或下载目录。

团队自建框架应优先补齐自己真正缺少的边界：统一环境、工具协议、日志、验收、权限与可恢复性。没有证据表明通用框架有瓶颈时，重写调度器未必比增加一个可靠测试入口更有价值。决定是否自建，要比较维护成本与反复发生的问题，而不是用框架代码行数证明能力。

8. 动手完成一次可复核的小闭环

练习一：按 S1—S5 写统计函数和 CLI。加入空文件、单样本、包含 NaN、乱序输入、偶数样本五类测试。预期结果不是“都输出一个数字”，而是非法输入明确失败、合法输入符合指定分位数定义，调用前后原序列不变。

练习二：故意把 ceil 改成 floor，检查测试是否真的能抓到。再让输出文件沿用旧运行标识，检查验收是否拒绝旧证据。如果这两种错误仍显示通过，先修验证系统，再谈让模型写得更多。

练习三：用不含真实账号的本地演示表单模拟截图缩放、按钮位置移动、提交后响应丢失。记录观察版本、动作与最终结果。预期能区分“未执行”“已成功”“结果未知”，而不是所有异常都归类为再点一次。完成后，你得到的是可解释的工作流，而不仅是一段漂亮的演示录像。
