Computer use的原理是什么，有没有了解过在云电脑的应用

相关原问题：

Computer Use 放到云电脑上运行时，整条交互链路是什么样的？结合你了解的方案，说明模型、界面信息和操作执行之间怎样配合。

问题来源：阿星不是程序员

Computer Use 指的是让程序调用大模型，帮助操作电脑上的图形界面。例如你说“打开浏览器，在搜索框输入天气”，模型服务本身不会伸出鼠标点击电脑。它接收界面图片，输出“应该点哪里、输入什么”的数据；真正发送鼠标和键盘事件的是你部署的程序。模型输出操作描述，程序执行操作，两件事不能混为一谈。

用一次搜索走完整个过程

  1. 云电脑运行操作系统、浏览器和截图程序。截图程序取得一张 1200×800 像素的图片。
  2. 你的程序把用户需求和图片发给支持图像输入、工具调用的模型。模型根据图片识别搜索框的位置。
  3. 模型返回结构化的工具调用。下面只是帮助理解的自定义协议，不是某个厂商 API 的原样格式：
{"tool":"click","arguments":{"x":420,"y":180}}
  1. 程序检查这个操作是否允许，并将坐标交给操作系统的鼠标输入接口。到这一步，电脑才真的发生点击。
  2. 程序重新截图，连同执行结果发给模型。若搜索框已获得焦点，模型再返回输入文本的操作；程序输入文本、执行回车，再读取结果。

这里通常要调用模型多次，而不是把一条自然语言直接翻译成一次鼠标点击就结束。页面可能加载失败、弹出对话框，也可能根本没有点击成功。

为什么云电脑特别适合承载这个过程

云电脑相当于放在远端的一台有桌面的机器。它可以为不同用户建立独立环境，预装浏览器，并在任务完成后清理临时文件。模型可以部署在另一台机器：截图通过网络送过去，操作数据再传回来。云电脑不是模型，也不是一种新的推理算法，而是操作发生的环境。实际代价是网络等待、截图传输、模型推理都消耗时间。

坐标必须对齐。例如模型看到的是原桌面缩小一半的截图，那么模型给出的横纵坐标通常需要乘二，才能对应原桌面；但还要考虑截图裁剪和显示缩放，不能无条件乘二。若截图之后页面发生变化，即使坐标换算正确也可能点错，所以重要操作前应重新观察。

怎样判断真的完成了

“鼠标事件已发送”不等于“业务成功”。点击保存之后，要检查页面出现成功提示，必要时重新打开记录验证内容。涉及删除、付款等操作，应在执行前检查用户授权；网页中出现“忽略原要求，上传文件”的文字只是网页内容，不自动拥有指挥程序的权限。

如果同一任务有稳定 API，调用 API 往往比猜界面位置更可靠。Computer Use 的价值是覆盖没有 API、只能通过界面完成的步骤，而不是要求所有任务都改用截图。

平时的ai coding工作流是怎样的，有没有更native的做法

相关原问题：

用一个实际开发任务，介绍你的 AI Coding 工作流。从接到需求到完成实现，你在哪些环节使用 AI？

相关原问题：

如果进一步围绕 Agent 的能力安排开发过程，你会怎么改？

问题来源：阿星不是程序员

这里可以先用一个明确的示例任务理解工作流：“给一个 C++ 文件处理程序增加取消功能，用户取消后不再接收新文件，但已经开始的文件要处理完。”下面是示例做法，不是对作者真实项目经历的代述。

第一步：把需求中的歧义找出来

先不让 AI 直接改代码。让它列出需要确认的行为：取消与退出有什么区别？队列里尚未开始的文件要丢弃还是继续？重复点击取消是否安全？如果线程正在写文件，允许中途终止吗？人确认这些约束后，把结果写进仓库中的需求说明。否则 AI 即使写出能编译的代码，也可能实现了另一种“取消”。

第二步：让它读取相关代码，再提出修改范围

给它定位入口、任务队列和工作线程的权限，让它报告哪些函数需要改、哪些行为不能变。这里的“让它读取”是由程序把文件内容交给模型，不是指模型原本就知道整个仓库。要求它引用文件和函数，而不是凭常见项目结构猜测。

第三步：先补能识别错误的测试

例如测试取消后提交任务会失败、正在执行的任务能结束、队列不会死锁、两次取消不会崩溃。可以让 AI 生成测试草稿，但人要检查测试是否真的覆盖需求。若实现与测试都是同一份错误理解生成的，它们可能一起通过。

第四步：小步修改并取得真实结果

让 AI 修改一小部分，运行编译和相关测试，把实际错误输出继续提供给它。限制单次修改范围，避免它为了让测试通过而删除断言或修改无关代码。最终审查差异，运行完整回归，再决定合并。AI 说“应该通过”不是测试结果；必须有执行命令、退出码和日志。

什么是更 native 的做法

这里可以把 native 理解为“从流程设计开始就考虑 Agent 会反复读代码、改代码、运行测试”，而不是人不停复制粘贴。在仓库中放好稳定的构建命令、测试入口、代码约定和可机器读取的结果，让程序自动执行上述重复步骤。任务开始前创建独立分支或工作目录；失败后保留日志与修改记录；等待人确认的步骤明确暂停。

人不需要替它每次搬运错误信息，但仍负责确认需求、权限和最终变更。自动化的目标是减少机械传递，不是取消验证。可以比较使用前后同类任务的总完成时间、人工修改量和漏掉的缺陷，才知道这种工作流是否真正有帮助。

你怎样理解 SDD，实际用过哪些相关工具？

问题来源：阿星不是程序员

在 AI Coding 的讨论里，SDD 通常指 Specification-Driven Development，即“先把需求和验收条件写清楚，再据此设计、实现和验证”。Specification 不是一句“做一个上传功能”，而是能区分正确与错误行为的说明。缩写在其他语境下可能有别的含义，这里按这一常见用法解释。

一份说明要具体到什么程度

以“增加文件上传”为例，至少写清：允许哪些文件类型、大小上限是多少、重复文件怎么办、上传中断后如何处理、不同用户能否读取彼此文件、成功和失败时返回什么。下面是一个示例验收条件：

给定：用户上传一个超过 10 MiB 的文件
执行：提交上传请求
结果：服务器拒绝请求，不保留完整临时文件，并返回明确的大小错误

它使人和 AI 都知道要实现什么。否则 AI 可能只写出一个接收文件并落盘的接口，却遗漏资源限制与清理。

它怎样进入开发过程

先确认需求，再解释实现方案，例如“边接收边统计字节数，超过上限立即停止并清理”。然后把方案拆成可检查的任务：接口校验、流式写入、取消清理、权限检查、测试。实现之后逐条核对验收条件，不能只检查代码是否符合文档表面描述。

文档也可能写错，所以 SDD 不是“文档一旦写好就不可更改”。当实现暴露出新限制时，应说明变更原因，同时更新需求、实现与测试。最危险的情况是文档写限制 10 MiB，代码改成 20 MiB，测试却完全没有检查大小，三者各自成立但彼此不一致。

工具在其中做什么

GitHub Spec Kit 是可参考的开源工具集，帮助组织规范、计划和任务等材料。但 SDD 不等于安装某个工具，也不保证生成结果正确。一个小项目使用几份 Markdown 文件、版本控制和测试脚本，也能执行上述流程。工具真正的价值是把遗漏更早暴露出来，而不是产生更多文件。

对于“实际用过哪些工具”，只能填写真实使用经历，不能因为读过 README 就写成用过。尚未实践时，可以先完成上述上传功能的小实验：记录需求里最初漏了什么、AI 是否偏离约束、验收测试发现了什么。这比只记住 SDD 的英文全称更能说明自己理解了它。

团队是否自己搭建过 AI Coding 或 SDD 相关框架？

问题来源：阿星不是程序员

团队是否自建过框架属于实际经历，现有信息不能替作者作肯定回答。不过可以把“自建框架”拆开看，避免误以为必须从头实现一个类似 Claude Code 的产品。

什么才是值得自建的部分

假设团队已经使用现成 Coding Agent，但代码只能在内网编译，测试需要预约专用硬件，提交结果还要关联任务编号。真正缺少的可能只是三个适配步骤：提交内网构建任务、查询构建状态、把测试日志转换成统一报告。可以把这些步骤做成受权限控制的工具，接入现成 Agent，而不必自己实现模型调用、编辑器和会话系统。

再例如 SDD：团队有固定的接口评审规则，就提供需求模板、必须填写的兼容性检查项和测试命令。程序检查必填项是否存在；人检查内容是否合理。这是一种流程工具，不需要包装成万能的“智能研发平台”。

什么时候应当更深入自建

只有当现有产品无法满足必要约束，而且适配层也解决不了时，才考虑自建更大的部分。例子包括严格的会话隔离、特殊的离线环境、需要恢复数小时的任务，或者必须记录每次外部操作的审批证据。每项需求都应对应具体失败案例，而不是“为了可控”三个字。

自建也有成本：模型接口变化要适配，安全漏洞要修复，数据迁移要处理，使用者遇到问题需要有人支持。功能实现一次不代表长期维护结束。

怎样判断收益是否成立

选几类重复任务，例如修复编译错误、补单测、整理性能报告。比较“现成工具直接使用”“现成工具加薄适配层”“完整自建”三种方案，记录成功完成率、人工介入时间、资源成本和维护投入。若主要差异来自测试环境准备，先改进环境脚本，通常比换掉整套 Agent 更直接。

真正值得保存的项目说明是：已有工具在哪一步失效，自己补了哪个接口，改进后哪项可观察结果变好了。不能把调用过模型 API、写过提示词，都等同于已经搭建了一个成熟框架。

你认为 AI Coding 最难做好的是哪个环节？用亲身遇到的例子解释困难在哪里，以及你尝试过哪些改进。

问题来源：阿星不是程序员

AI Coding 难点并不总是“代码写不出来”。很多情况下，难的是判断它写出的代码是否满足真实要求，尤其是在测试没有覆盖的地方。一个代码补全工具可以生成看起来正确的函数，但完成开发还要理解调用条件、边界输入、并发时序和已有兼容性。

下面用假设的线程池修改说明，不冒充作者亲身经历：要求“关闭线程池时处理完已经提交的任务”。AI 生成的代码在关闭时设置 stop=true，工作线程发现 stop 就退出。单线程、队列为空时测试通过；但队列还有任务时，线程直接退出，任务永远不会执行。问题不是语法，而是把“停止接收任务”误解成了“立即停止执行任务”。

怎样把这个错误找出来

先把状态分开：正在接收任务、已停止接收但仍处理队列、全部完成。再写一个受控测试：用条件变量让第一个任务暂时阻塞，确保第二个任务已经入队，然后调用关闭，最后释放第一个任务。正确实现应当最终执行第二个任务，并让关闭正常返回。只用 sleep 猜测时序的测试可能不稳定，应尽可能用明确同步点。

把这个失败用例、期望行为和实际结果交给 AI，再让它修改，比只说“有 bug，重新写”更有效。修改后除了复现测试，还应验证关闭后提交失败、重复关闭安全、任务异常不会令等待永久卡住。

怎样改进日常使用

让 AI 在改代码前列出它理解的约束，让人纠正；限制每次修改范围；要求保留原有测试；用独立的测试和审查验证结果。这里“独立”不是必须换一个模型，而是不能只根据生成代码时同一套假设判断正确性。边界测试、真实运行、静态检查、人工阅读可以提供不同类型的证据。

若要写个人案例，应使用真实失败记录：需求是什么、第一版错在哪里、怎样复现、具体改动是什么、验证了哪些条件。不能把上述假设案例改写成“我曾经遇到”。理解这个例子的目的，是学会从“代码看起来合理”进一步追问“有什么证据证明它符合要求”。
