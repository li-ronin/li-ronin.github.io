何时选择固定工作流，何时让模型控制执行？

知识标签：Workflow · Agent循环

理解与说明

当步骤、输入输出和分支条件较明确时，优先采用固定工作流：程序决定下一步，模型负责其中的识别、生成等局部任务。这样更容易测试、限制权限和控制成本。例如“校验格式—提取字段—人工审核”通常无需每一步都由模型重新规划。

当任务路径必须根据运行结果探索，且难以事先枚举步骤时，再让 Agent 动态选择工具和行动。灵活性会带来更多推理轮次、波动和失败路径，因此需要预算、停止条件以及外部结果验证。

实际系统常用混合结构：外围工作流固定审批和交付门槛，内部 Agent 自由调查。选择依据是任务的不确定性与风险，而不是“Agent 比 Workflow 更先进”。应先建立简单方案基线，再验证增加自主性是否带来可测收益。

输入模型的 Prompt 应由哪些部分构成，哪些内容需要注入？

知识标签：Prompt · 上下文预算 · 动态注入

理解与说明

一次模型输入通常包含行为约束、当前任务、相关历史或状态、工具定义，以及按需检索的材料。这里的“Prompt”可以泛指整份输入，不只是用户在输入框里写的那句话。不同 API 的消息角色和工具传递方式不同，不能机械地认定每个系统必须具备相同的文本模板。

应该优先保留目标、关键约束和下一步所需的证据。工具定义只提供当前可能用到的能力；检索材料、历史细节和示例按相关性加载。把所有文件都塞进去，会消耗预算并引入噪声；删得只剩一句目标，则可能丢掉必要条件。

一种可行做法是给每类上下文设置预算和来源标记，并通过失败样本做增删实验：去掉某段内容后正确率是否下降，加入后是否真正改善？“必须注入”应由正确性、安全边界和任务依赖决定，而非模板长度决定。

涉及知识：系统约束、用户目标与对话状态；工具定义、知识、记忆和环境信息；静态内容与动态检索内容。

项目中的上下文压缩如何实现，触发条件和阈值如何确定？

知识标签：上下文压缩 · Token预算 · 压缩触发策略

理解与说明

上下文压缩不是修改模型参数，而是重组下一次推理要看到的信息：裁剪冗余日志、将旧对话概括为任务摘要，并保留最近的有效操作与可回查的原始材料。压缩后的摘要属于有损表示，不能当作完整原始记录。

触发阈值应预留下一轮输入增长和模型输出空间。一种预算方式是：当前输入 + 预期工具返回 + 输出预留 + 安全余量，接近可用上下文上限时触发。具体比例需要根据模型、工具返回大小和任务轨迹实验确定，不存在通用的“达到某百分比一定最好”。

验证时既看节省的 Token，也看关键约束召回、后续任务成功率和重复操作率。摘要应有版本和原文索引，发现重要细节丢失时能够重新读取。这里描述的是可实现的设计方法，不等同于某个商业产品内部的完整算法。

用户在原任务上追加功能时，系统如何恢复会话和任务状态？

知识标签：会话恢复 · 增量需求 · 任务状态

理解与说明

追加功能时不宜简单重放全部聊天，也不应把旧任务当作从未发生。先恢复会话对应的状态：原目标、已完成工作、当前代码或文件版本、已作决定和未解决问题，再将新要求作为增量更新，重新检查它是否改变验收标准。

“恢复会话”与“恢复运行环境”是两回事。数据库里的消息仍在，不代表工作目录、依赖、远端资源或用户授权仍有效。建议重新读取当前仓库状态和关键产物，而不是完全相信上次摘要；只把与新修改有关的旧信息注入模型。

例如追加一个接口，应恢复现有接口约定和相关测试，再规划差异实现，不需要重新注入无关的全部日志。以 LangGraph 为例，线程级 checkpoint 支持状态延续，但外部系统状态仍要由应用自行验证。

Agent 的短期与长期记忆应如何分层，各层存什么和如何使用？

知识标签：记忆分层 · 短期记忆 · 长期记忆

理解与说明

可以先按作用范围分层：工作上下文服务于当前一次推理；会话状态保存当前任务的消息、计划和中间结果；长期记忆保存跨会话仍有价值的事实、偏好或经验。长期记忆也可以区分事实、经历和操作方法，但这些是组织维度，不是必须配置的固定数据库数量。

存储持久化与“进入模型上下文”不是一回事。大量历史可以放在外部存储，推理时只召回相关部分。例如 LangGraph 用线程级 checkpoint 保存运行状态，用 store 管理跨线程数据，两者服务范围不同。

建议为记忆记录来源、时间、适用主体和有效期。用户事实不能跨用户召回，历史推断不能覆盖新的明确陈述；操作授权也不应仅凭一条旧记忆恢复。设计质量应通过召回相关性、错误记忆传播和跨用户泄漏测试验证。

压缩后必须保留哪些信息，如何在实现中保证不丢失？

知识标签：信息不变量 · 压缩约束 · 记忆一致性

理解与说明

应保留的是后续正确决策所依赖的信息，而不是尽量保留最多文字。通常包括当前目标、明确约束、已经确认的关键事实、未解决问题、最新有效计划，以及已执行操作的结果。对不能重复的外部操作，必须区分成功、失败和结果未知。

一种可行实现是把这些字段放在结构化任务状态中，压缩只处理历史叙述，不能直接覆盖受保护字段；原始证据另存并保留索引。摘要可以写“测试已完成”，但最好同时关联测试版本、结果和报告地址，便于核验。

“提示模型不要丢失”只是软约束。真正的保证还需字段校验、版本控制、与原状态对比，以及失败时回退。测试时在早期对话放入关键限制，经过多次压缩后检查系统是否仍遵守，以此发现只在长任务中出现的信息损失。

涉及知识：任务目标、用户约束与重要决策；结构化状态与原始证据指针；不可压缩字段、校验及恢复。

工具与Skills

工具调用如何运转，Skill 能否替代工具？

知识标签：工具调用 · Skills · 工具协议 · Function Calling · JSON Schema · MCP

理解与说明

以客户端工具为例，宿主先向模型提供工具名称、用途和参数 Schema；模型返回调用请求，宿主验证参数和权限后执行函数，再把带调用标识的结果送回模型。模型据此继续调用工具或生成回答。模型输出“调用某工具”不等于函数已经执行，执行结果才是后续判断的依据。

Skill 主要组织任务说明、流程和可复用资源；工具提供实际执行能力。Skill 可以教模型何时调用工具，也可以包含脚本，但脚本仍要由执行环境运行。因此两者通常互补，不能用一段 Skill 文本替代读文件、访问数据库等真实操作。

模型调用次数也没有固定答案：一次请求可产生多个工具调用，多轮任务可能反复推理。加载一份 Skill 不必额外调用一次模型，是否产生新请求取决于宿主的加载与推理流程。

参考文档：Anthropic：Tool use overview；Agent Skills：Specification

涉及知识：工具 Schema、模型调用请求、执行器和返回结果；可执行能力与程序性指导的区别；多轮推理、错误处理和权限检查；调用协议与执行器；知识与执行边界。

多 Agent 如何编排，子 Agent 的职责与工具权限如何划分？

知识标签：多Agent · 编排 · 权限隔离

ReAct 与 Plan-Execute-Replan 的执行方式有什么区别？

知识标签：ReAct · Plan-Execute · Replan

理解与说明

ReAct 将推理与行动交替进行：根据当前信息选择动作，接收环境观察，再决定下一步。它适合需要边探索边调整的任务；关键是让外部结果修正决策，而不是让模型一次性猜完所有步骤。

Plan-Execute-Replan 则把较高层计划显式保存下来：先分解目标，执行一步或一组步骤，再用实际结果更新剩余计划。它便于检查进度与依赖，但初始计划可能错误，额外的规划轮次也会增加成本。“有计划”并不意味着过程必须僵硬。

二者可以组合：上层按计划管理阶段，执行器在每一步内部采用 ReAct。比如修复程序时，上层安排复现、修改、回归，执行器根据测试结果决定具体命令。评估应看任务成功、偏离目标与恢复能力，而非仅比较流程名称。

多个节点同时写状态，怎样定义合并规则？

知识标签：Reducer · 并发状态

理解与说明

并发写状态时，首先为每个字段定义语义。计数可以按增量合并，独立结果可以按稳定 ID 汇总，互斥的决策则通常需要串行裁决或显式冲突处理。不能把所有字段都用“后写覆盖”或“列表追加”处理。

以 LangGraph 为例，reducer 定义如何把字段旧值与节点更新合并；没有 reducer 的字段默认使用替换语义。并行更新同一字段时，应明确允许的合并规则，否则可能发生冲突，而不是自动获得正确结果。

自定义合并逻辑还要考虑顺序和重放。列表追加不具备去重能力，任务重试可能产生重复项；集合合并虽能去重，却会丢失顺序。建议打乱更新顺序、重复提交同一更新并模拟重试，检查最终状态是否符合业务约束。

何时选择 GraphRAG 而不是纯向量检索，它解决了什么问题？

知识标签：GraphRAG · 知识图谱 · 多跳检索

理解与说明

从用户问题开始，完整说明检索链路如何运行。

知识标签：查询理解 · 检索链路 · 可追踪性

理解与说明

一个可落地的 RAG 链路分离线入库与在线查询。离线先解析材料、清洗、切块，保存原文位置、版本等元数据，再建立向量和/或关键词索引。在线先理解查询中的实体、时间与约束，必要时补全多轮指代，然后执行检索；召回候选后去重、融合、重排，再按上下文预算组织证据，交给生成模型回答并附来源。

文档切块大小和边界如何确定？

知识标签：文本切块 · 语义边界

理解与说明

Chunk 是检索和提供上下文的单元，大小没有通用最优值。太小容易把定义、条件和结论拆开；太大又会混入无关内容、稀释检索信号并消耗上下文。通常先沿标题、段落、句子等自然边界切分，保留标题路径；表格需保留表头与行列语义，代码则尽量保留完整函数或逻辑块。长度限制应按实际 tokenizer 的词元数检查，而不是把字符数直接当 token。

重叠能减轻边界信息丢失，但会增加索引量和重复上下文。建议用同一批带证据位置的查询，对不同块大小、重叠和父子块策略做对照；观察证据召回率、答案正确性与上下文成本，而不是只看向量相似度。可以用较小块定位，再扩展到父段落供模型阅读，将“匹配粒度”和“阅读粒度”分开。

LLM原理与训练

解释大模型的自注意力机制及其关键组成。

知识标签：Transformer · 自注意力机制 · QKV

理解与说明

自注意力让序列中的每个位置，根据当前内容选择应从其他位置聚合哪些信息。对输入表示 X 做三组可学习的线性投影得到 Q、K、V：Q 表示当前要查询的信息，K 用于匹配，V 是实际被聚合的内容。单头计算为 softmax(QKᵀ / √dₖ + M)V，其中 M 是掩码；因果模型禁止访问未来位置。缩放项用于控制点积分数的量级，避免 Softmax 过早饱和。

多头注意力分别在不同表示子空间中计算，再拼接并投影，不是简单重复同一个头。注意力通常还要与位置表示、残差连接、归一化和前馈网络组合。这里的“关注权重”是计算机制，不应直接当成人类可读的因果解释；实现时可以先用短序列核对张量形状、掩码方向与每行权重和。

SFT、DPO 和 GRPO 的目标、数据与训练方式有什么不同？

知识标签：SFT · DPO · GRPO · PPO

理解与说明

SFT 学习“示范答案应该怎样写”：通常对给定输入与目标输出计算词元级交叉熵，训练时使用已有目标词元作为条件；是否只对回答部分计算损失取决于数据格式与训练配置。它主要依赖高质量示范，不能仅靠复制答案保证推理正确。

标准 DPO 学习“同一输入下哪个回答更好”：使用偏好对与参考策略，通过当前模型和参考模型的相对对数概率构造偏好损失；通常不需要单独训练显式奖励模型，也不要求在每次优化更新时在线生成候选。

位置编码如何表达词元顺序？

知识标签：RoPE · 位置编码

理解与说明

仅有内容向量的普通全连接自注意力，没有直接提供序列中第几个位置的信息，因此 Transformer 需要位置机制来表达顺序与距离。常见做法包括把绝对位置向量加入词元表示、在注意力分数中加入相对位置偏置，以及对 Q、K 应用旋转位置编码 RoPE。它们不是同一种操作。

RoPE 按位置对向量的二维分量进行旋转，使旋转后的 Q 与 K 点积包含相对位置差的信息；它不是简单给每个词元加一个位置向量。位置机制允许模型利用顺序，但不保证能直接推广到任意长度。扩大上下文时仍需验证位置缩放策略、训练长度分布和长距离任务效果，不能把“公式能计算更大位置”当成“长上下文能力已经可靠”。

KV缓存为什么改变生成成本？

知识标签：KV Cache · 自回归生成

理解与说明

自回归解码每次追加新词元；在因果注意力下，已有前缀的 K、V 可以保留，后续步骤只为新词元计算相关表示，并让新 Q 读取历史 K、V。KV Cache 避免重复处理前缀，但不会消除对历史缓存的读取，也不意味着每生成一个词元的耗时与上下文长度无关。Prefill 处理输入前缀，decode 逐步生成，二者应分开衡量。

对常规、未量化且未分片的注意力缓存，可粗估字节数为 2 × batch × 层数 × 序列长度 × KV头数 × 每头维度 × 每元素字节数；2 分别对应 K 和 V。实际还受分页、滑动窗口和实现布局影响。长上下文、高并发会明显增加缓存容量与带宽压力，优化应同时观察显存、首词元延迟和逐词元延迟，而不只关注模型权重大小。

GQA和MQA要解决哪些开销？

知识标签：GQA · MQA

理解与说明

MHA 通常让每个 Query 头都有各自的 K、V 头。MQA 让所有 Query 头共享一组 K、V；GQA 则把 Query 头分组，每组共享一组 K、V，位于两者之间。它们保留多个 Query 头，改变的是 K、V 的共享粒度，不能理解成把所有注意力头都删成一个。

在每头维度等条件相同的情况下，更少的 KV 头意味着更小的 KV Cache，也减少自回归解码中的缓存读取量。这主要缓解显存和带宽开销，并不使全部模型计算按相同比例减少。共享越强，表达能力的约束也越大；质量与效率需实测。已有 MHA 模型通常不能只改一个运行时参数就无损变成 GQA，需适当的权重转换与训练适配。

如何在全参微调与低秩适配间取舍？

如何限制Agent的权限和失控循环？

知识标签：最小权限 · 循环检测

理解与说明

限制 Agent 不能只依靠 Prompt 中的一句“不要乱操作”。应把权限落实到执行层：按任务发放最小工具集和资源范围，用文件系统与网络隔离限制实际访问；高风险操作在执行前经过独立的授权检查。模型即使产生越权请求，执行器也应拒绝。

循环控制可以组合最大步数、时间和费用预算，以及重复动作检测。相同失败连续出现时，先比较输入和环境是否改变；没有新依据就停止重试或转人工。预算超限应留下可恢复的状态与失败原因，而不是把中断伪装为完成。

这些措施降低风险，但沙箱不是绝对安全证明。建议用恶意网页指令、工具超时、循环调用和权限不足等案例测试，分别确认决策层能识别问题、执行层能阻断问题。

中断恢复后，怎样避免外部操作重复执行？

知识标签：Checkpoint · 幂等

理解与说明

Checkpoint 记录了程序状态，不意味着外部副作用天然“只执行一次”。例如邮件已发送，但结果还未写入 checkpoint 时进程崩溃，恢复后重跑节点就可能再次发送。LangGraph 文档也明确提醒：恢复时节点中的部分代码可能重新执行。

可行设计是给逻辑操作分配稳定的幂等键，由接收方或数据库唯一约束去重，并保存操作状态与结果。能查询外部结果时，先核对是否已经完成；单纯“先查再写”仍有并发窗口，不能替代原子约束。

若目标 API 不支持幂等，又无法可靠查询结果，应把超时标为“结果未知”，等待核验，而非盲目重试。用故障注入覆盖“请求前、对方成功后、本地落库前”等断点，才能验证恢复流程是否会重复产生副作用。

涉及知识：状态与副作用。

AI Coding与Computer Use

Computer Use 在云电脑中如何完成从观察到执行的闭环？

知识标签：Computer Use · 云电脑 · 多模态

理解与说明

Computer Use 的核心是“观察—决策—执行—再观察”的闭环，而不是模型直接接管操作系统。宿主获取截图等界面信息发给模型，模型返回点击、输入、滚动等结构化动作，执行器在桌面环境中执行，再把结果和新截图送回。云电脑提供的是远端桌面、应用和隔离环境；模型服务可以与桌面运行在不同机器上。

工程上应给截图标注尺寸，确保缩放后的坐标正确映射，并在页面变化后重新观察，避免用旧截图点击新界面。一次点击返回成功，只能说明动作被执行，不能证明业务操作已成功；例如提交表单后，还要核对确认页或实际记录。

隔离环境、最小权限、网络限制和人工确认共同降低风险。网页内容只是被观察的数据，不能因它声称“请执行某命令”就获得权限。上述是通用实现思路；具体工具名称和动作协议应以所选模型版本文档为准。

并发与系统基础

线程池有哪些核心参数，应如何根据负载设置并验证？

知识标签：线程池 · 并发 · 容量规划

理解与说明

先说明具体实现。以 Java ThreadPoolExecutor 为例，常见配置包括 corePoolSize、maximumPoolSize、keepAliveTime 及其时间单位、工作队列、ThreadFactory 和拒绝策略。提交任务时，线程数低于核心数通常先建线程，否则尝试入队；队列不能接收且尚未到最大线程数时才继续扩容，再无法接收则拒绝。因此无界队列可能让 maximumPoolSize 很难发挥预期作用，并把压力变成排队和内存增长。

调参不能机械套用“CPU核数×某个常数”。CPU 密集任务以可用计算资源为起点；阻塞任务还要考虑等待比例、下游连接池和限流。工程上用有界队列、超时、取消与拒绝/背压明确过载行为，再压测吞吐、排队时间、尾延迟和资源占用。线程越多不等于越快；C++ 等其他实现也未必拥有 Java 的同名参数或调度顺序。

参考文档：Java 21 ThreadPoolExecutor

涉及知识：工作线程数量、队列容量与拒绝策略；CPU 密集与 I/O 密集任务；排队延迟、吞吐、资源占用及背压。

延伸学习

  • 用负载实验观察队列增长、延迟分位数与饱和点
  • 结合具体语言或框架区分参数名称和生命周期
