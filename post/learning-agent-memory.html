问题来源：阿星不是程序员

Agent 的“记忆”通常不是把模型重新训练了一遍，而是程序把需要保留的信息写到文件或数据库，并在以后合适的时候读出来、放进模型输入。所谓长短期，主要区别在保存多久、服务什么任务，以及什么时候读取。

先用一个开发任务区分

你正在修复 sum.cpp：刚读出的源码、当前报错、上一轮尝试，是短期工作内容。这个项目规定“必须用 C++17，测试运行 ctest”，可能要跨很多次会话使用，是项目长期信息。你明确要求“解释代码时先讲整体流程再逐行分析”，可能是跨项目也有用的个人偏好。这几种东西不应全部混在一个无限增长的聊天记录里。

一种可实现的分层是：

  1. 当前上下文：正在解决的问题、最近相关材料。要求及时、精确，但容量有限。
  2. 当前任务记录：已完成步骤、未解决问题、对应文件和证据。可以在中断后恢复，任务结束后不必每轮加载。
  3. 项目长期记录：构建方法、稳定约定、重要设计原因。切换到相关项目时读取。
  4. 用户长期偏好：明确、持续有效的习惯。按相关性使用，不能覆盖本次明确要求。

这是设计示例，不是唯一标准。小项目可以合并部分层，关键是作用范围和更新规则清楚。

静态长期记忆和动态长期记忆为什么分开

这里“静态”通常指人维护、变化较少的规则，例如语言版本、代码规范；“动态”指在工作过程中新增或修正的经验，例如“某种测试必须先设置一个环境变量，已在某版本验证”。静态不是永不修改，动态也不是模型说什么都写进去。

分开有两个好处：首先，模型归纳的一次经验不会悄悄覆盖人工规则；其次，可以采用不同审查和过期策略。项目升级后，动态经验可能已经失效，需要重新验证；用户维护的规则也可能通过明确修改更新。

一条长期记录至少需要什么

除了内容，最好保存作用范围、来源、记录时间、验证状态和被哪条新记录替代。例如：

内容：项目 A 的测试需要启用 feature_x
来源：构建配置与一次实际测试日志
适用版本：提交 abc123 附近；升级后需复查
状态：已验证，不是所有项目的通用要求

示例提交号不代表真实项目。若只存一句“测试要开 feature_x”，以后换项目就可能错误套用。

不同层有哪些约束

短期报错不能自动成为长期事实；长期记录不能无条件全部塞进每次输入；私有项目材料不能因语义相似而召回给另一个用户；历史允许的操作不等于当前仍有权限。新需求与旧偏好冲突时，应使用当前明确要求，并记录旧项是否被替代。

可以用“换项目、隔天恢复、用户纠正偏好”三个实验测试分层是否有效。能存下来只是第一步，能在正确场景读出、遇到过期信息不误用，才说明记忆设计有价值。

每一轮对话触发一次长期记忆存储，有没有出现用户长期记忆快速积累，存的过多？

每轮对话都检查“是否有值得记住的信息”可以，但每轮都新增一条长期记忆通常没有必要。否则一句“这次先用 Python”可能被误存成永久偏好，重复对话又会产生很多相同记录。

为什么会越存越乱

假设一天有 100 轮对话，每轮都写一段总结。一个月就是几千条，其中很多只是进度、临时报错或已经过期的计划。以后检索“项目测试命令”，可能同时找到旧命令、新命令和一次失败尝试，模型难以判断该信哪一条。问题不仅是磁盘容量，更是错误信息进入当前输入。

因此要区分三种存储：完整会话日志用于追溯；任务状态用于恢复未完成工作；精选长期记忆用于以后复用。保留日志不意味着每条日志都应该参加记忆检索。

写入前可以做哪些判断

先判断是否可能跨会话有用，再判断是否有可靠来源、是否已有同义记录、是否只是临时要求。用户明确说“以后都这样解释”，与“今天先这样处理”不同；工具实际验证过的结果，与模型自己猜测的原因也不同。

一个简化流程是：提取候选 → 判断作用范围 → 查找已有记录 → 选择新增、更新、忽略或标记冲突。不要只做“追加”。例如项目测试命令从 A 改成 B，应把 A 标为被替代并链接新来源，而不是让两条都以同样权重存在。

去重不是只比较字符串

“使用 C++17”和“这个仓库的标准是 C++ 17”可能是同一件事；但“项目 A 用 C++17”和“项目 B 用 C++17”作用范围不同，不能随便合并。可以先通过关键词或向量找候选，再按主体、范围、时间和来源判断。模型辅助合并时，应保存原始记录，避免合并错误无法恢复。

过期与容量怎样控制

有明确时效的信息设置复查时间，例如临时环境配置。无效、被替代、长时间未使用的记录不再默认召回，但审计记录可以保留。给每次召回和每个项目设置预算，避免数量增长就把全部信息塞进 Prompt。隐私敏感或凭据信息不应随意写入这种通用记忆。

评价时至少看重复率、过期信息被召回的比例、错误记忆导致的错误，以及确实帮助完成任务的比例。不能只报告“存了多少条”。一个小实验是连续三次描述同一个偏好，再明确纠正一次：正确结果应是当前有效版本清楚，而不是四条互相矛盾的句子同时出现。

大模型怎么决定长期记忆是否需要召回？

模型不会天然知道你在外部数据库里存了哪些记忆。要让它决定是否召回，程序必须给它某种入口，例如“搜索项目记忆”的工具；也可以由程序先按规则检索，再把相关结果交给模型。两种做法可以组合。

三种常见方式

第一种是规则先行。用户打开项目 A，程序自动加载项目 A 的少量稳定规则，例如编译标准和测试入口。这类内容通常每次都相关，不必让模型重新判断。

第二种是模型按需搜索。用户问“上次为什么不用方案 B”，当前输入没有答案，但工具说明告诉模型可以搜索历史决定。模型生成查询，程序在允许访问的记录中检索，把结果返回。模型再判断是否足以回答。

第三种是混合方式。程序先找少量可能相关的记录，模型发现缺少细节时再发起搜索。这样可以降低漏查，但要限制候选数量，避免检索把无关历史带进来。

一个完整例子

用户说“继续昨天的空数组问题”。程序首先用用户、项目和任务标识找到昨天任务记录，而不是仅靠“空数组”在所有人的记忆里搜索。记录写着“空输入已修复，整数溢出未处理”，并给出源码和测试日志位置。模型读取这段记录后，再通过工具确认当前代码，继续未完成部分。

这里至少有两次不同的读取：检索历史记录帮助确定背景，读取当前文件帮助确认事实。不能把记忆检索结果当成当前仓库的完整状态。

检索结果怎样筛选

先按权限和项目范围过滤，再比较内容相关性；之后检查更新时间、来源、是否已被替代。相似度高只能说明句子相近，不说明内容仍正确。结果应该附简短来源和适用范围，让模型知道“这是某次任务记录”，而不是一条普遍真理。

还应允许没有结果。找不到可靠记录时，系统可以重新读取资料或说明无法确认，不应为了保持流畅编造“你上次决定了什么”。若旧记录与用户最新要求冲突，以当前明确要求为准，并检查旧记录是否需要更新。

怎样知道召回策略有效

建立几类测试：无需历史就能回答、必须依赖历史、历史已经过期、存在相似但属于另一个项目的记录。观察必须召回时是否找到正确材料，不需要时是否引入噪声，越权材料是否始终不可见。

所谓“模型决定”只是一种选择方式，不应同时承担权限判断。即使模型选择了搜索另一个项目，程序也必须独立检查访问范围。把这两件事分开，才能避免模型一次错误选择变成数据泄露。
