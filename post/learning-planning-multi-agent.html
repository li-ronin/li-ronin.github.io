1. 计划不是一段更长的思维描述

一个任务如果只有“读文件，回答问题”两步，未必值得引入显式计划。复杂任务的困难是：中间结果会改变下一步，部分工作可并行，部分工作必须等待，还有一些动作一旦做错就难以撤销。计划的价值是把这些依赖与验收条件显式化，让系统知道何时能开始、何时该停止。

以“修复序列化器的空数组崩溃，同时保证兼容性”为例，可以拆成复现、定位、修改、定向验证、回归验证和交付。每个步骤都应有输出，而不是只有动词。例如“定位”输出候选根因、证据引用和仍未排除的解释；“修改”输出相对基线的差异；“验证”输出绑定代码版本的测试结果。

如果计划写的是“分析问题、深入思考、努力解决”，它无法被执行器检查，也无法在失败时决定回到哪里。好的计划不是保证未来不会变化，而是让变化可以被识别和处理。

2. ReAct 与 Plan-Execute-Replan 不是二选一

ReAct 论文研究将推理与行动交织，使模型在行动后利用观察更新判断。工程上可以把这种思路理解为短循环：观察现状，选一个动作，检查结果，再决定下一步；不要把论文方法直接等同于某个产品完整运行时。参考：ReAct。

Plan-Execute-Replan 则把相对高层的任务结构外显出来：先形成计划，执行当前可开始的步骤，遇到新证据后更新计划。它不是必须对应三次模型请求；规划可能由规则完成，执行步骤也可能是确定性的测试命令。关键是有没有明确的计划状态与修改条件。

二者可以嵌套：外层计划要求“先复现，再修复，再验证”；内层定位阶段用多个读文件与搜索动作逐步缩小范围。若每遇到一条新日志都重做全局计划，会浪费推理并造成抖动；若执行到底不允许调整，又会把错误假设一路传播。

3. 用依赖图决定哪些工作可以并行

设 R 是复现故障，A 是检查公开接口契约，F 是修复实现，T 是运行测试，V 是最终复核。R 与 A 可以并行；F 依赖两者，T 依赖 F，V 依赖 T 与差异记录。节点的关系不是“谁看起来独立”，而是它读取的数据是否已经稳定，是否会与其他节点写同一资源。

假设 R 需要 6 分钟，A 需要 4 分钟，F、T、V 分别需要 8、3、2 分钟。全串行是 23 分钟；R 与 A 并行后的理想下界是 max(6,4)+8+3+2=19 分钟。即使加入十个 Agent，也无法突破这条关键路径，协调开销还可能抵消 4 分钟收益。这些是假设数值，用来说明分析方法，不是性能基准。

一个调度器可以先检查依赖是否完成，再派发 ready 节点，收到结果后更新状态。下列伪代码省略线程池实现，但保留了版本检查与状态机。运行中的任务不能因为收到新计划就当作从未执行过，取消也要核实是否已经产生副作用。调度器还必须检测无可运行节点的阻塞状态；否则某个前置节点需要复核时，下游可能永远等待不会到来的结果。等待也必须有截止时间，超时后先核实在途任务，而非假定它们已停止。

while not all_finished(plan):
    ready = [n for n in plan.nodes
             if n.status == "pending"
             and all(plan[d].status == "accepted" for d in n.dependencies)]
    for node in ready:
        node.status = "running"
        dispatch(node, input_snapshot=state.revision)

    if not any(n.status == "running" for n in plan.nodes):

4. 重规划必须有触发依据和停止预算

最初怀疑是空指针，复现后发现只在特定编译选项下失败，这就是假设被证伪；测试环境缺依赖，则是执行前提不成立；用户追加“保持旧格式兼容”，则是目标约束变化。三者都可能触发重规划，但处理方式不同：改变定位路径、修复环境、补上兼容性步骤。

不要因为某次工具失败就立即重写全部计划。先区分可重试的暂时错误、无效输入、权限不允许以及根因假设错误。给每个节点设置重试上限，给整体设置时间、成本和无进展上限。连续三次重复读取同一证据却没有新假设，通常需要停止或升级，而不是让 Agent 自动多思考几轮。

计划本身也应版本化，保留修改理由和被替代步骤的状态。历史结果不是全部作废，但必须检查其前提是否仍然成立。基于旧工作区运行的测试，不能在代码改变后继续作为最新验收证据。

5. 子 Agent 的区别应体现在输入、输出和权限

一种教学分工是：侦察者只读代码并提出定位证据；实现者在隔离工作区改代码；验证者独立运行测试并检查差异；协调者维护任务状态和交付。区别不在角色名字有多像公司组织，而在每个角色的职责、工具集合、上下文和结果契约是否不同。

侦察者的输出可以是文件位置、可复现条件、候选根因、置信依据和反证。它不应该修改实现；实现者也不能只交付“已完成”，而要交付 patch、版本、变更解释和未验证项。验证者若看到实现者的自信结论后照抄，便没有提供独立验证价值。

所有子 Agent 共享所有工具，确实配置简单，却扩大误操作影响，增加工具选择噪声，也让职责边界失去作用。工具代码可以共享，授权范围不必共享。反过来，限制过严又会导致每一步都等待协调者，应根据任务所需最小权限设计，而非追求形式上的绝对隔离。

6. 并行最大的坑是状态合并，不是同时启动

如果两个节点同时写 summary 字符串，“后写覆盖前写”可能丢掉另一份发现；简单拼接又可能制造重复和矛盾。应先决定每个字段的语义：事实证据是以稳定标识合并的集合，日志是有事件标识的序列，当前版本由单一协调者更新，互斥结论进入待裁决列表，而不是自动覆盖。

LangGraph 的状态字段可以定义 reducer 来处理更新；未定义特殊 reducer 的字段通常采用替换语义。框架提供合并机制，不会替你决定业务上什么才算正确合并。参考：State 与 reducer。

下面的集合合并在元素具有稳定标识且不可变时满足交换、结合和幂等，适合重放或乱序到达。若同一个 id 对应不同内容，必须作为冲突处理，不能静默选择一个。两份 patch 修改同一行，也不能靠字典合并解决，需要版本控制或重新分工。

def merge_evidence(left, right):
    merged = dict(left)
    for key, value in right.items():
        if key in merged and merged[key] != value:
            raise ValueError("conflicting immutable evidence")
        merged[key] = value
    return merged

B = {"trace-1": ("revision-A", "null access")}
assert merge_evidence(A, B) == merge_evidence(B, A)
assert merge_evidence(A, A) == A
assert merge_evidence(merge_evidence(A, B), A) == merge_evidence(A, B)

7. 协作协议不能替代分工设计

MCP 面向应用接入工具和资源等能力；A2A 面向 Agent 之间的任务交互与能力描述。它们能降低部分互操作成本，但不能自动回答“谁负责最终正确性”“失败时谁恢复”“结果冲突谁裁决”。这些仍是应用设计问题。参考：A2A 规范。

同一进程中的多角色函数不一定需要 A2A；多个独立部署、需要协商任务生命周期的 Agent 才更可能受益于跨 Agent 协议。先决定部署边界和互信关系，再决定协议。用协议名称代替架构理由，会掩盖额外网络故障和身份管理成本。

多 Agent 还会增加重复上下文、协调消息和合并验证成本。总成本应计入所有模型请求、工具资源、失败重试和人工复核；延迟看关键路径，而不是各 Agent 时间的平均值。并行缩短等待不意味着减少总算力，也不意味着结论更正确。

8. 先证明分工有效，再增加 Agent 数量

用相同任务集比较单 Agent、固定工作流和多 Agent。固定模型、工具、上下文额度与停止条件，再分别记录任务成功率、修改冲突数、重复调查量、总 token、端到端耗时和人工介入次数。复杂方案若只在最容易的任务上变快，却在失败恢复上更脆弱，就不能称为整体改进。

  1. 手工画一个任务依赖图，给每个节点写出输入、输出、前提、完成条件和失败去向；找出关键路径。
  2. 让两个只读节点乱序返回并重复提交同一证据，运行上面的 reducer 断言；再故意制造相同 id 不同内容，确认系统报告冲突。
  3. 在实现者运行途中改变目标约束，检查哪些节点结果仍有效，哪些需要取消或重做。不要仅在 UI 上改计划文字。
  4. 删除一个子 Agent，比较成功率与成本。如果没有损失，说明这个角色也许只是增加了组织形式，而非增加能力。
