说下线程池的核心参数，以及参数设置的经验？

线程池可以理解为“一批长期存在的工作线程，加上一个等待任务的队列”。提交任务时不必每次创建线程：空闲线程从队列取出任务并执行。它解决的不是让 CPU 凭空变快，而是减少反复创建线程的开销，并控制同时进行多少工作。

先明确这里说的是 Java 的七个构造参数

ThreadPoolExecutor 的常见完整构造函数包含：

  • corePoolSize：核心线程数。通常在线程数不足这个值时，为新任务创建线程；不是默认启动时就全部创建。
  • maximumPoolSize：允许的最大线程数。
  • keepAliveTime：空闲线程等待多久后可以退出。
  • unit：上面时间值的单位。默认主要用于超过核心数的线程，核心线程超时需要额外配置。
  • workQueue：暂时不能执行的任务放在哪里，以及最多能放多少。
  • threadFactory：怎样创建线程，例如名称与异常处理配置。
  • handler：池无法接收任务时怎样处理，即拒绝策略。

用一个例子理解提交顺序

假设核心数为 2，最大数为 4，队列容量为 2。暂时假设所有已开始的任务都没有结束：前两个任务创建两个线程执行；第三、第四个任务进入队列；第五、第六个任务因为队列已满，才会创建额外线程；第七个任务无法入队，也不能再增加线程，进入拒绝处理。因此，不是先创建到最大线程数，再开始排队。真实并发过程中线程可能随时结束，例子只是隔离出来说明规则。

若使用几乎不会满的无界队列，任务通常一直排队，最大线程数很难发挥扩容作用，内存和排队时间反而可能不断增长。直接丢弃也不一定合适：例如生成账单不能静默丢失；让调用者收到明确繁忙错误并稍后重试，通常更容易维护正确性。

参数怎样估算

CPU 密集任务主要在计算，可先从可用 CPU 核数附近开始测试，线程更多未必更快。I/O 密集任务经常等待网络或磁盘，可以允许更多线程，但必须同时检查数据库连接数、下游限流和内存。

一个仅用于初步估算的例子：平均每个任务占用线程 0.2 秒，每秒到达 20 个任务，平均同时占用约 20×0.2=4 个线程。4 只是平均需求，没有包含突发、长尾和安全余量，不能直接作为最终配置。再以 4、8、16 个线程分别压测，观察完成吞吐、队列长度、超时率，以及 95% 请求能在多久内完成。若从 8 加到 16 后吞吐不升、延迟变差，应找下游或锁竞争，而非继续加线程。

C++ 标准库没有一套与这七项一一对应的通用线程池接口。自己实现时仍要决定线程数、队列边界、停止规则、异常传播和拒绝方式，但不能把 Java 的参数名当成所有线程池必备的标准。

流式上传与响应如何避免资源耗尽？

问题来源：TrustZone

流式处理是指数据分段到达时就逐段处理，不必等全部数据收齐。例如上传大文件时，服务器收到一块就写入文件；模型生成回复时，生成一部分就发给客户端。它可以减少等待和内存占用，但前提是程序真的逐段处理，而不是把所有分段又追加到一个无限增长的数组里。

慢消费者为什么会造成问题

假设服务器每秒产生 1 MB 数据，客户端每秒只能接收 0.2 MB，中间缓冲区每秒就增加 0.8 MB。如果没有上限，任务持续越久，占用内存越多。这和线程池任务队列不断积压是同一类问题。

背压就是让下游来不及处理时，上游减慢或暂停，而不是继续无限生成。实现可能是等待可写事件、使用有界队列，或在超过限制时取消任务。并不是所有外部模型服务都能暂停生成，因此有时必须终止请求，而不能无限缓冲。

上传要检查什么

限制单文件总大小、每个用户的并发上传数和临时文件占用；边接收边计算字节数，超过上限立即停止。不要只相信请求头宣称的大小。客户端断开、解析失败或超时后，需要关闭文件并清理不完整内容。

模型流式回复要检查什么

设置最大输出量和总时间；客户端取消时，把取消传到后台任务和可取消的模型请求；关闭不再需要的连接。如果前端已经停止显示，而后台继续生成几十分钟，用户看不到结果，费用与资源却还在消耗。

对于特别长的结果，可以保存成文件并提供链接，而不是必须全部保存在内存中。不过文件也要受访问权限和保留规则约束。

怎样测试

故意让客户端很慢，观察内存是否稳定；上传到一半断开，检查临时文件是否清理；同时发起多条长请求，确认达到上限后明确拒绝或排队。正常网速下能显示逐字输出，只能证明功能存在，不能证明资源受控。
