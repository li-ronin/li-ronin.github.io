1. 并发、并行和排队不是同一个量

并发表示多个任务处于进行中，并行表示同一时刻有多个任务真正执行。线程池复用线程，避免为每个任务无限创建线程，但它不会凭空增加 CPU、磁盘或下游服务容量。队列只是把暂时不能执行的任务保存起来；队列增长不是系统正在消化压力的证据，可能恰好说明它已经消化不过来。

把一个任务的时间拆成排队时间 Wq 和实际服务时间 S，用户感受到的是 W=Wq+S。线程池常常只让你看到活跃线程数，却不自动告诉你队列中最老任务已经等了多久。对于 Agent 服务，模型请求、文件解析、向量检索、外部API各有独立容量，不应该用一个“最大并发”概括所有瓶颈。

2. 用一个算例判断队列为什么必然增长

假设每个任务占用一个工作线程 50ms，且这段时间基本不变。单线程服务能力约 1/0.05=20 个任务每秒，4 个线程的理想上限约 80 个每秒。如果到达速率也是 80，每个小抖动都没有空闲余量吸收；实际服务时间有方差时，排队会很敏感。若持续到达 100 个每秒、处理只有 80，队列大约每秒多 20 个任务。扩容队列只能推迟溢出。

粗略利用率可写为 ρ=λE[S]/c，其中 λ 是到达速率，E[S] 是平均服务时间，c 是工作线程数。这是帮助识别容量的简化模型，不是任意系统的精确延迟公式。稳定运行通常需要留余量；把 c 从4改成8也未必翻倍，因为下游数据库可能只允许4个连接，剩余线程只是阻塞着等连接。

在稳定且统计口径一致的系统里，Little定律 L=λW 连接平均在途任务数、完成速率与平均停留时间。例如平均在途20个、每秒完成100个，则平均停留约0.2秒。它不直接给出p95，也不能拿不断堆积的过载阶段套出一个稳定结论。测量时先确认系统是否达到稳态。

3. 线程池参数只有放进调度顺序里才有意义

以 Java 21 ThreadPoolExecutor 为例：未达到核心线程数时通常先建线程；否则尝试把任务入队；队列无法接收且未达到最大线程数时再扩容；仍无法接收则触发拒绝策略。因此“核心4、最大100、无界队列”并不意味着高负载时很快产生100个线程，任务可能主要堆进队列。还需要理解空闲回收时间、线程工厂和关闭语义。参考：Java线程池调度说明。

C++ 自建线程池不一定具有同样参数和顺序。设计时先回答：队列是否有界；满了是立即失败、等待还是由调用者执行；关闭后是否接受新任务；取消是否会移除尚未执行的任务；任务异常由谁接收。参数名可以不同，但这些语义不能省略。

拒绝不是系统失控的同义词。若服务不能无限承诺未来的计算，及时返回过载比让请求等待几分钟后超时更诚实。调用者执行策略也有边界：如果调用者是UI线程或事件循环，运行重任务会阻塞其他请求；它不是可以无条件套用的背压方案。

4. 一个可编译的有界队列核心

下面只实现队列，不宣称是完整生产线程池。生产者使用 try_push，满或关闭时立即失败；消费者等待数据，关闭后继续取完存量，再返回空值退出。使用谓词等待防止虚假唤醒。示例任务用整数代表，便于先检查生命周期，再替换成真实任务对象。

#include <condition_variable>
#include <cstddef>
#include <mutex>
#include <optional>
#include <queue>
#include <stdexcept>
#include <utility>

template<class T>
class BoundedQueue {
    std::mutex m_;
    std::condition_variable ready_;
    std::queue<T> q_;
    std::size_t cap_;
    bool closed_ = false;
public:
    explicit BoundedQueue(std::size_t cap) : cap_(cap) {
        if (cap == 0) throw std::invalid_argument("zero capacity");
    }
    bool try_push(T item) {
        {
            std::lock_guard<std::mutex> lock(m_);
            if (closed_ || q_.size() >= cap_) return false;
            q_.push(std::move(item));
        }
        ready_.notify_one();
        return true;
    }
    std::optional<T> pop() {
        std::unique_lock<std::mutex> lock(m_);
        ready_.wait(lock, [&] { return closed_ || !q_.empty(); });
        if (q_.empty()) return std::nullopt;
        T item = std::move(q_.front());
        q_.pop();
        return item;
    }
    void close() {
        {
            std::lock_guard<std::mutex> lock(m_);
            closed_ = true;
        }
        ready_.notify_all();
    }
};

互斥锁保护的不是某一个 push，而是“检查状态与改变状态”的整体：若先检查容量再在锁外入队，两个生产者可能同时看到剩余一个位置。notify_one 放在解锁后，避免刚唤醒的消费者立即争用同一把锁；正确性主要由受锁保护的条件和谓词保证。close 必须 notify_all，因为多个消费者都需要醒来看到关闭状态。

这个实现选择“排空后关闭”，不是“立即丢弃”。使用者必须保证关闭并等待所有工作线程退出之后才销毁队列，否则仍在等待的线程会访问已销毁对象。若 T 的移动操作可能抛异常，还需明确异常安全策略；真实任务常可用只移动的智能指针包装，避免复杂对象在队列内部搬运。

5. 队列容量如何和延迟预算联系起来

假设8个工作线程每个任务50ms，队列允许32个等待任务。在所有任务耗时接近且线程持续繁忙的理想情况下，队尾任务约需等待32/8×50=200ms，再服务50ms。这个估算不是尾延迟保证，但说明“队列越大越好”与低延迟目标矛盾。面对长尾任务、锁竞争或下游超时，实际等待可能更长。

每个任务应带截止时间，而不只是全局超时。任务真正开始前检查是否已经过期；已经没有价值的请求继续占用资源，会让还没过期的请求也排到过期。取消信号要传到下游，否则客户端关闭连接后，后台仍可能继续生成长回答、上传文件和消耗费用。

容量还要按字节估算。32个小整数和32份百兆上传文件完全不同；按任务数限流不能限制总内存。可以把大文件落到受控临时存储，队列里只保留引用，并同时设置单任务大小、总暂存容量和清理生命周期。

6. 流式传输为什么仍会爆内存

“边读边发”只描述接口形态，不自动提供背压。假设上游每秒产生10MB，下游只能消费2MB，如果每次收到数据都追加到内存列表，缓冲区每秒增长8MB，一分钟接近480MB。即使HTTP使用分块传输，应用层仍会积压。真正的背压要把下游处理能力传回上游，让生产暂停、降速或拒绝。

Node.js 的 writable.write 返回 false 时，调用者应等待 drain 再继续生产；标准 pipeline 能协调流和错误。这是具体运行时的接口，说明了通用机制：消费者发出“暂时没有容量”，生产者遵守它。不能把 false 当作写入失败再重复写同一块。参考：Node.js背压机制。

while (chunk = read_next_chunk()):
    if request_cancelled(): stop_upstream(); break
    await downstream_capacity()
    await write_chunk(chunk)
    release_local_reference(chunk)

对于模型流式响应，上游可能仍在远端生成；暂停本地读取未必能立即停止计费或计算。需要核对服务的取消语义，并给中间缓冲区明确上限。日志、追踪和重试缓存也必须有界，否则主输出有背压，旁路日志仍可能把内存耗尽。

7. 两个隐藏陷阱：线程饥饿与重试风暴

线程池任务 A 提交任务 B 到同一个已经满载的池，然后阻塞等待 B；若所有线程都在等这样的子任务，就没有线程能执行 B。这不是互斥锁循环才会出现的死锁，而是资源耗尽形成的等待环。解决方向包括避免工作线程同步等待同池子任务、拆分执行器或用异步依赖，但要根据任务语义选择。

另一个陷阱是把过载错误当成必须立刻重试。下游容量已经不足，上游所有任务同时重试，会进一步放大负载。应限制重试次数和总时间，加入退避与抖动，并仅对可安全重试的操作重试。重复创建等副作用需要幂等机制；网络错误不是无限重放业务动作的许可。

8. 实验：用证据找线程数和队列长度

先做确定性检查：容量2的队列连续推3个元素，前两个成功，第三个失败；关闭后拒绝新元素，但之前两个仍可读，之后 pop 返回空值。再用多个生产者和消费者运行唯一ID任务，检查每个被接受的ID恰好处理一次、被拒绝的ID没有执行，并确认所有线程可正常退出。

负载实验固定任务内容，逐步提高到达速率，分别记录接收量、拒绝量、完成量、在途量、排队时间、服务时间和端到端p50/p95/p99。任务包括纯CPU、固定阻塞以及混合长尾三种。预期在持续过载时，有界方案开始拒绝但内存保持受控；无界方案短时间可能“零拒绝”，却伴随越来越长的排队。

最后把下游连接数固定为4，线程数依次改为4、8、16。若吞吐不再增长而等待和上下文切换增加，说明瓶颈并不在线程数量。能解释这一曲线，比记住一个线程数公式更重要。本文数值是分析与实验设计，不是声称已在你的机器或业务中得到的测量结果。
