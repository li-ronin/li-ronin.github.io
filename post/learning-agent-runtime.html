DeepSeek harness和pi的区别是什么

相关原问题：

怎样比较 DeepSeek harness 和 pi 的设计？

问题来源：阿星不是程序员

如果原题中的两个名称分别指 DeepSeek 官方的 deepseek-ai/deepseek-harness，以及原 badlogic/pi-mono、现转到 earendil-works/pi 的 Pi，那么可以比较它们的程序组织方式。这里按 2026-10-21 阅读到的官方仓库与文档说明；原题没有给版本，因此下面不代表某个早期版本，也不把其他同名项目混进来。

先弄清它们与模型的关系

模型负责根据输入生成回答或工具调用请求；Harness 是包在模型调用外面的程序，负责提供工具、执行请求、保存会话和整理下一次输入。比如模型返回“读取 sum.cpp”，真正打开文件的是 Harness 中实现的函数。使用同一个模型，也可以搭配不同 Harness，所以不能把它们的区别简单说成“用了不同大模型”。

DeepSeek Harness 主要怎样组织

官方架构文档强调基于 Cordis 组织插件。模型适配、工具注册、会话记录，甚至默认 Agent 循环本身，都按插件组织，可以通过配置组合或替换。这里“插件”是能被程序加载的代码模块，不只是提示词文件。

这意味着开发者想改某个组成部分时，重点是找到对应服务接口和插件注册位置，而不一定直接修改一个不可替换的大主程序。它也要求理解插件之间的依赖、加载和卸载过程。官方仍提示预览阶段可能出现兼容性变化，因此自建扩展要锁定版本并测试升级。

Pi 主要怎样组织

Pi 官方将自己定位为较小、可扩展的 Agent Harness。它提供扩展模块、Skills、提示词模板等定制方式；扩展代码可以注册工具、监听事件、修改上下文或增加命令。官方 README 特别说明，子 Agent 和 Plan 模式等做法不作为其默认核心功能强行规定，可以通过扩展或其他组合实现。

因此不能说“Pi 没有扩展能力”，也不能把“默认不内置某流程”说成“永远做不到”。它倾向于保留较少的固定工作方式，让使用者按自己的任务组合。扩展运行在 Pi 进程权限下，这也意味着扩展来源必须可信，不能把插件机制误认为安全隔离。

两者最重要的不同是什么

可以把重点放在“哪些东西可替换、通过什么方式替换、默认提供什么”上：DeepSeek Harness 把较多系统组成部分统一放进插件组合体系；Pi 通过较小的基础程序和扩展接口让使用者定制工作方式。两者都不是只写提示词，也都不因为可扩展就自动更准确。

例如想增加一个 C++ 测试工具，两边都要实现真实运行函数、参数说明和结果返回。想改变多 Agent 的安排，则要进一步检查各自当前版本的扩展或插件接口，不能仅看首页口号判断改动成本。

怎样比较实际效果

用同一模型、同一代码起点、同一批任务，记录成功率、模型调用、工具错误、恢复表现和总成本；另做一次扩展开发，比较新增工具需要改哪些文件。本文没有运行这样的对比实验，所以不宣称谁更快或更强。架构差异可以从官方代码确认，效果优劣必须由具体任务验证。

Claude code与codex他们各自有什么特别？

Claude Code 和 Codex 都可以理解为“能够读取项目、修改文件、运行命令并根据结果继续工作的编程助手”，不是只能在聊天框里输出代码。比较时必须先说明是在比较产品程序、底层模型，还是自己的使用体验，否则很容易把三件事混成一句“谁更聪明”。

先说共同流程

当你要求“修复失败测试”时，两类工具都需要获取源码和报错，让模型生成下一步请求，再由实际程序读取文件或运行测试。模型不能只凭一句“已经修复”证明磁盘改动正确。工具权限、工作目录、测试环境和输入材料，都会影响最终结果。

例如一个在本地能访问构建工具，另一个远程环境没装依赖，二者表现不同首先可能是环境差异，不是模型推理能力差异。

可以有依据地比较哪些特点

按本文核对的官方资料，Claude Code 的产品文档较完整地说明了 Skills、自定义子 Agent、项目指令、权限配置等使用方式。它使用 Claude 系列模型，学习它时可以从“如何把项目说明、工具和子任务组合进实际工作”入手。

Codex 也有命令行等使用形态，公开的 openai/codex 仓库可以用于研究实现；项目规则可以通过 AGENTS.md 提供，安全配置需要区分沙箱限制和执行审批。沙箱限制程序能访问什么资源，审批决定某些操作是否需要用户确认，二者不是同一开关。

这里列的是能从官方资料核对的特点，不表示某项能力只有一方存在。产品持续更新，也不能沿用早期文章中的功能缺失结论。阅读源码时应固定提交号；比较使用行为时应记录版本、模型和配置。

用什么任务比较更有意义

可以准备三类任务：修复一个有明确测试的缺陷；实现一个跨文件的小功能；审查一份包含已知问题的代码差异。给两者相同的仓库起点和需求，保留日志，再看：

  • 是否正确理解限制，有没有改无关文件。
  • 是否真的运行验证，还是只生成解释。
  • 失败后能否定位原因，是否反复做相同尝试。
  • 总耗时、Token、人工介入次数是多少。

如果实际使用的是不同底层模型，报告应该说“这两个产品与模型组合的表现”，不能把差异全部归因于 Harness。若要研究程序设计本身，最好控制模型与工具条件，无法控制的因素要写出来。

学习时怎样选择切入点

想看具体代码怎样处理模型请求、会话和执行，公开源码是一个直接入口；想理解一项产品的用法，先按官方教程复现一个小任务。不要一开始就背很多功能名。把“用户输入 → 实际发送材料 → 工具请求 → 执行结果 → 下一次请求”记录下来，再看两者在哪些步骤不同，会比“某个更适合思考、某个更适合执行”这样的笼统评价更准确。

你做的coding agent和Claude code与codex区别在哪？

这个问题必须依据自己的项目回答，不能仅凭“我做了记忆、多 Agent、Skill”就判断比 Claude Code 或 Codex 有优势，因为成熟产品也可能具备相近能力。真正需要说明的是：你的系统针对什么具体需求做了不同选择，这种选择带来了什么可验证的效果和代价。

先把比较对象放在同一层

Coding Agent 是一个应用系统，包含模型调用、工具执行、上下文整理、状态保存和用户界面。更换底层模型与修改 Agent 程序不是同一件事。如果你的项目只是把 API 从模型 A 换成 B，差异主要是模型选择；如果你增加了专用测试器、权限规则和恢复机制，差异才涉及程序设计。

比较时还要写清产品版本和使用形态。例如本地命令行运行与远程任务环境不能直接混为一谈。自己能调用一个专用内网接口，而别的产品在你的环境里没配置这个接口，也不等于它从设计上绝对不支持。

用一个假设项目说明回答方式

假设开发了一个专门修复 C++ 测试失败的 Agent。它的不同之处可以是：每次修改前强制保存复现结果；只允许写指定源码目录；修改后必须运行原失败用例及相关回归；程序中断后按调用记录恢复，而不是重复运行未知结果的操作。

这些是示例设计，不是你的真实经历。要把它变成可信比较，需要准备同一组缺陷、同一仓库起点、相同可用工具和尽可能接近的模型条件，比较修复成功率、错误修改、耗时和成本。否则更好的结果可能来自模型差异，而不是自己的系统设计。

不能只说优点

专用流程可能在某类任务上更稳定，但处理临时探索问题时不如通用产品灵活；严格验证可能增加耗时；自建工具需要维护；多 Agent 会增加调用费用和合并冲突。说明这些代价，比声称“比现成产品更智能”更有内容。

还要明确哪些功能已经实现并测试，哪些只是计划。例如代码里有恢复入口，不代表在断电、工具超时、写文件中断等情况下都验证过。可以展示一次真实故障和对应日志，说明系统怎样继续或停止。

形成一段有证据的介绍

可以按“具体用户问题 → 现有做法在该环境中的不足 → 自己改了什么 → 怎样测量 → 结果与限制”组织。所需材料是项目代码、设计记录、测试任务和运行结果，而不是背一段通用答案。

如果当前只是学习原型，也可以如实写明“实现了工具调用和会话保存，尚未完成与成熟产品的对比评测”。这不是答案不完整，而是把已做的工作和想做的工作准确分开。

整个链路运转的流程？

先从一个你能观察到的任务说起：用户输入“修复 sum.cpp 中导致空数组测试失败的错误”。Coding Agent 不是把这句话交给模型后，模型就直接修改磁盘。实际工作由“模型生成请求”和“普通程序执行请求”交替完成。

1. 第一次请求发给模型的是什么

负责运行 Agent 的程序先整理输入：用户的问题、项目规则、已知文件信息，以及可用工具的说明。例如它告诉模型，有一个 read_file(path) 工具可以读文件，有一个 run_test(name) 工具可以运行测试。这里的“工具”就是程序已经实现好的函数，不是模型临时想象出来的能力。

模型可能返回下面这样的数据。它是示意格式，不是某家 API 的原样字段：

{"call_id":"c1","tool":"read_file","args":{"path":"sum.cpp"}}

模型输出了一条“希望调用 read_file”的结构化请求。此时文件还没有被读取，更没有被修改。就像你在纸上写 ifstream("sum.cpp") 并不会真的打开文件一样，必须有程序去执行。

2. 谁真正读文件、改代码

Agent 程序收到请求后，检查工具是否存在、参数是否正确、路径是否在允许范围内。如果可以执行，才调用读文件函数，把内容以 c1 对应的结果返回。调用编号用于防止多个工具结果混在一起。

程序把这个结果加入下一次模型请求。模型这次看见了源码，可能要求运行失败测试，再根据报错生成补丁。写文件函数执行补丁前，还要检查文件是否被其他人修改。修改成功后再次运行测试，测试输出又成为后续模型输入。

完整顺序可以是：用户需求 → 模型请求读文件 → 程序读文件 → 模型请求运行测试 → 程序运行测试 → 模型给出补丁 → 程序修改文件 → 模型请求复测 → 程序复测 → 模型解释结果。不是每个任务都必须走同样顺序，但模型不能凭空知道未被提供的源码和测试结果。

3. 为什么还需要保存状态

“状态”就是程序需要记住的数据，例如当前任务、已经执行的调用编号、补丁、测试退出码、剩余预算。模型请求失败后可以重试，但已经执行过的写入不能不检查就再次执行。测试超时也不能被当成测试通过。

一个最小实现应在每次模型请求前检查总次数和时间限制；在工具执行后保存结果；在报告完成前核对实际文件差异和测试结果。模型可以输出“已完成”，但应用程序仍应检查完成条件。检查日志时，应该能逐条找到：输入、工具请求、真实执行结果、后续处理。缺少执行结果，便不能证明对应操作发生过。

延伸问题

以下是根据外部资料另外整理的问题，不是上面原记录的逐字转录。

何时选择固定工作流，何时让模型控制执行？

问题来源：代码随想录

固定工作流是程序预先规定步骤和分支；让模型控制执行，是程序把当前情况交给模型，由它选择下一步调用哪个工具或是否结束。两者并非只能选一个：外层可以固定，某个步骤内部再让模型选择。

先看一个不需要自由选择的任务

处理报销单通常已经有明确顺序：读取字段、检查金额和凭证、交给有权限的人批准、记录结果。即使使用模型识别票据文字，也没有必要让模型自行决定要不要跳过审批。这里把关键步骤写成程序，通常更容易测试和解释。

再看步骤事先不确定的任务

排查一个陌生项目的编译错误时，下一步取决于刚看到的内容。模型可能需要先读头文件，再查宏定义，或者直接运行一个最小用例。把每种可能都写成固定分支会非常复杂，所以可以让模型在允许的只读工具中选择。

例如程序提供 read_file、search_text 和 run_test 三个工具，模型返回工具名与参数，程序检查并执行，再把结果发回。自由选择的只是这些允许范围内的下一步，不是允许模型执行任意操作。

选择时看哪些条件

步骤是否稳定、错误代价多大、能否检查结果，是比“任务复杂不复杂”更有效的问题。固定且高风险的步骤适合程序明确控制；探索性强但可验证的步骤适合模型参与。若任务本身没有可靠的成功标准，让模型不断尝试可能只是在增加成本。

还可以采用混合方式：程序固定要求先建立工作副本、最后运行测试；中间如何定位问题由模型选择；合并代码仍需满足审核条件。

怎样比较效果

用同一组真实任务比较两种实现，记录完成率、工具调用次数、耗时和人工干预。若固定流程已经覆盖大部分需求，增加自由规划却没有明显提高成功率，就没有必要为了“更像 Agent”而采用它。设计应从需要解决的问题出发，而不是从框架名称出发。

LangGraph的复杂度在哪些业务中值得承担？

问题来源：TrustZone

LangGraph 适合用来表达有多个步骤、分支和可保存状态的任务。可以先把 graph 理解成流程图：节点是一段处理逻辑，边表示接下来可能走向哪里；state 是这些步骤共享并更新的数据，例如用户问题、检索结果和当前状态。

哪些任务容易从它受益

假设一个文档处理任务需要读取材料、抽取字段、等待人工审核，再提交结果。人工审核可能几小时之后才发生；服务可能重启；某一步失败后希望继续而不是从头处理。这时需要保存进度、恢复执行和记录状态变化，框架提供的相关机制可能比自己零散拼接更容易维护。

另一个例子是并行查询多个来源，然后统一整理结果。明确写出并行分支和汇合位置，有助于检查哪些数据已经准备好。

为什么简单任务未必需要

如果任务只是接收一句问题、调用一次模型、返回答案，用普通函数就能很清楚地表达。加入图状态、节点定义和检查点存储，可能增加学习、部署和调试成本，却没有解决真实问题。

即使使用框架，也仍要决定状态字段怎么设计、并行更新怎样合并、外部操作怎样避免重复。这些业务问题不会因为用了 graph 自动消失。尤其是恢复执行可能重新运行部分代码，发信或写数据库等动作仍需专门处理。

一个实际判断方法

先画出自己的任务流程，再标记三个地方：是否会等待外部输入，是否需要跨进程恢复，是否存在复杂分支和并行。如果这些都没有，先用普通代码；如果有，尝试用小范围原型实现最难的一条路径，比如“审核前服务重启，审核后能继续”。

比较引入前后的代码复杂度、测试难度和故障恢复表现，而不只比较正常路径写了几行。框架值得承担的复杂度，是它帮助消除的那些重复而容易出错的工程工作；不是为了让架构图更丰富。

运维Agent如何从告警走到可验证的处理闭环？

问题来源：讨个offer咯

运维 Agent 处理告警时，不能只把日志交给模型，让它直接执行一条“修复命令”。完整任务应该从确认告警开始，到验证服务恢复结束；中间哪些操作可自动做，必须事先确定。

用磁盘空间告警作例子

收到“磁盘使用率高”之后，先确认是哪台机器、哪个挂载点、数据是否最新。只读检查可以查看空间占用、增长速度和相关服务状态。模型根据这些信息提出可能原因，例如某个日志目录快速增长，但这还不是已经确认的事实。

程序再执行经过允许的查询，验证哪个目录、哪些文件实际占用空间。不能直接按文件名猜测“都是临时日志，可以删除”。它可能包含仍被进程打开的文件，也可能是必须保留的业务数据。

修复前需要哪些条件

明确操作范围、风险、回退办法和批准人。低风险且已约定的动作可以自动执行；可能丢数据或影响服务的动作应先确认。例如调整日志轮转与删除历史文件不是同一风险，不能因为二者都能释放空间就随意替换。

每个动作记录目标、参数、开始时间和结果。请求超时还要确认操作是否已经发生，避免重复执行。

修复后验证什么

不只看命令退出码。检查空间是否下降、服务是否仍正常、错误率是否恢复、告警是否重新触发。若空间只是短暂下降但仍快速增长，根因可能没有解决，应继续调查或转人工。

这里所谓完整处理，是“有证据确认问题，有依据采取允许的措施，有指标检查结果”，不是给流程起一个复杂名字。

怎样先做一个安全版本

先让 Agent 只读诊断并给建议，人工执行修复；积累真实案例后，只开放少数经过测试、可恢复的操作。用历史故障回放和故障演练验证，不能以一次成功演示作为自动管理生产环境的依据。

从Prompt到Context再到Harness，治理边界如何扩大？

问题来源：AIGC小白入门记

这几个词容易被说得很抽象，可以用同一个例子区分：你希望 AI 修复一个编译错误。

Prompt 在这里指给模型的指令文本，例如“请解释错误原因，并尽量做最小修改”。改善 prompt，就是把任务和输出要求说明得更清楚。但如果没有把真实报错和代码给模型，再好的措辞也不能让它知道缺失信息。

Context 指这次请求中模型实际能看到的信息，例如用户需求、相关代码、错误日志、以前的工具结果和工具说明。管理 context，就是决定哪些内容要提供、怎样组织、何时更新，避免无关日志挤掉关键约束。不同讨论中 prompt 有时也泛指整个输入，两者不是严格统一的互斥术语，这里只是为了说明设计关注点。

Harness 在 Agent 工程里通常指包在模型周围、让任务能够执行的程序系统。它发送模型请求，解析工具调用，检查权限，运行工具，保存状态，再把结果发回模型。它不是模型内部的一层神经网络，也没有一个所有产品都必须遵守的唯一结构。

为什么只改文字不够

假设模型输出“读取 src/main.cpp”。这只是请求数据；必须有程序真正读取文件并返回内容。如果模型请求删除仓库，提示词写了“不要删除”仍不够，执行器应当有实际权限限制。如果任务中途断电，聊天提示也不会自动替你保存进度。

所以所谓关注范围扩大，具体就是从“怎样说清楚任务”，扩展到“给它哪些事实”，再扩展到“程序怎样安全地执行、记录和验证”。不是前一个概念被后一个淘汰，三者仍然一起工作。

怎样学习更容易理解

先实现一个只有两种工具的小程序：读文件和运行测试。打印每次发送给模型的输入、它返回的工具名与参数、程序执行结果。你就能直接看见文字指令、输入材料和执行代码分别在哪里，而不是只背概念。

这个解释描述通用工程分工，不代表某个厂商内部实现，也不能据此推断所有名为 harness 的开源项目具有相同功能。

面向用户的Agent应用应如何划分架构模块？

问题来源：AIGC小白入门记

面向用户的 Agent 应用可以先按“谁负责什么”拆开，而不是一开始就拆成很多微服务。小型项目完全可以放在一个进程里，只要职责清楚、便于测试。

从一次用户请求看模块

  1. 交互入口接收用户输入，展示进度和最终结果，例如网页或命令行。它不能把前端隐藏按钮当作真正权限控制。
  2. 任务管理为请求分配编号，记录正在运行、等待确认、失败或完成，并处理取消与超时。
  3. 模型调用部分整理要发给模型的消息和工具说明，调用模型服务，解析返回文本或工具请求。
  4. 工具执行部分核对参数和权限，执行文件、搜索或业务接口操作，返回实际结果。模型返回“调用成功”不是这一层的替代品。
  5. 数据存储保存需要恢复的任务状态、必要记录和产物引用。不同用户的数据要隔离。
  6. 验证与监控检查结果是否满足任务要求，并记录失败、耗时和费用，帮助定位问题。

用“生成文档草稿”走一遍

用户提交主题，入口建立任务；模型请求查资料；工具执行器根据用户权限查询并返回材料；模型生成草稿；程序检查输出文件是否存在且能打开；入口提供下载。如果用户要求发送给别人，应该作为新的明确操作检查收件人与授权，不能因为草稿生成成功就自动发送。

模块之间传什么

尽量使用有含义的字段，例如任务编号、工具名、参数、退出状态和结果位置，而不是让每个模块都从一长段自然语言里猜信息。原始文本适合表达开放内容，状态字段适合表示必须明确判断的事实。

错误也要保留类型：模型超时、权限拒绝、工具执行失败和结果验证失败不能全部变成“系统错误”，否则不知道应该重试、修正参数还是交给人。

什么时候再拆服务

只有在并发、隔离、部署周期或团队边界确实需要时，再把工具执行器或任务队列拆到独立服务。过早拆分会增加网络故障、认证和数据一致性问题。先用最小可运行流程证明任务有价值，再根据实际瓶颈扩展，比先画出十几个组件更稳妥。
