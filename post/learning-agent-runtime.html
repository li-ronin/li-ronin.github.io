1. 模型会提出行动，但运行时决定行动能否发生

设想你向系统提出：“修复一个 C++ 序列化器处理空数组时的崩溃，保持公开接口不变。”模型可以判断应该读哪些文件、提出修改、解释测试结果；但模型本身并不会因为输出“执行测试”这几个字就创建进程。真正打开文件、修改工作区、启动编译器的是程序。理解 Agent 的第一步，是把推理能力与执行责任分开。

本文把 Harness 或运行时作为教学中的工程概念：它负责组装上下文、调用模型、解释模型响应、检查行动边界、执行工具、记录结果、决定是否继续，以及恢复中断任务。不同项目对 Harness 的命名和边界可能不同，不能看到这个词就假定它是一个确定的产品或算法。

你可以把它类比为一个事件驱动服务：模型是可替换的决策依赖，工具是受控的外部适配器，任务状态是业务数据，运行循环是控制流。一个外观像聊天框的系统，内部仍然需要普通软件工程中的超时、错误处理、权限、审计和测试。

2. 从一句需求走到一个可验证结果

首先把需求转换为任务状态：目标是“不再崩溃”，约束是“公开接口不变”，完成条件是“复现测试由失败变成功，相关回归测试通过”。如果完成条件只写“模型说修好了”，运行循环会在最容易自信而非最可靠的位置停止。

然后固定一个工作区快照或记录起始版本，准备最小上下文：用户需求、约束、仓库说明、相关目录和工具定义。模型返回两类结果之一：普通文本，或结构化工具请求。工具请求先经过参数校验和授权检查，执行结果再作为观察进入下一次推理。这个过程可以重复多轮。

在例子里，观察不是只有成功结果：搜索没找到函数、编译失败、测试触发段错误，都是改变下一步判断的证据。一个真正闭环的系统会根据这些观察调整动作，而不是先生成十步命令后不看输出地全部执行。最终还要独立验证工作区差异、接口变化和测试记录，再生成交付说明。

Anthropic 对工作流与 Agent 的公开区分，强调预先定义的路径与模型动态决定流程之间的不同。它是一种设计分析方法，不是把所有系统硬分成两类的定律。参考：Building effective agents。

3. 一段能读懂的运行循环

以下为 Python 风格伪代码，目的是暴露责任边界，不是某个 SDK 的直接用法。model.decide 的返回值必须经过协议解析；dispatch 只能访问注册过的工具，不能把任意模型文本当作 shell 命令。verify_acceptance 是任务特定的验证器，而不是另一个“你觉得完成了吗”的自由回答。

计数器必须在每次模型请求尝试时递增，不能只在工具执行后递增，否则模型反复要求结束、却验收失败时会绕过步数上限。总时间和 token 预算另行检查，有限步数不等于有限单步耗时。幂等键绑定同一逻辑操作及其重试，不能仅按工具参数去重，因为用户可能有意重复相同操作。特别注意 finished 和 accepted 不同。前者只是模型想结束，后者表示系统拿到了足够证据。对于无法自动验证的任务，可以返回“等待人工复核”，而不是强行把成功写进状态。

while state.model_attempts < limits.max_model_attempts:
    enforce_deadline_and_token_budget(state, limits)
    request = build_context(state, evidence_store)
    state.model_attempts += 1  # 每次请求尝试都计数，包括失败和提前结束
    reply = model.decide(request)
    events.append("model_reply", reply)

    if reply.kind == "final":
        verdict = verify_acceptance(state, workspace)
        if verdict.accepted:
            return deliver(reply.text, verdict.evidence)
        state.add_observation(verdict.missing)
        continue

    call = parse_registered_tool_call(reply)
    validate_schema(call)
    authorize(call, user_constraints, current_scope)
    key = get_or_create_key(call.logical_operation_id)  # 同一意图重试沿用，新意图新键
    result = execute_with_record(call, key, timeout=30)
    state.apply_observation(result)
    checkpoint(state)
    state.tool_executions += 1

return needs_review("预算耗尽", state.evidence_refs)

4. 可靠性最难的地方是“可能已经执行了”

假设工具已经创建了一个远端工单，响应却在网络中丢失。运行时看到超时，并不能推出“没有创建”。如果直接重试，可能创建两张工单。这里需要区分三类结果：确定成功、确定失败、结果未知。未知是一种需要查证的业务状态，不应被压成普通异常字符串。

对于读取文件这样的操作，重试通常不会增加副作用；对于扣款、发消息、推送或删除，必须结合操作身份、下游支持的幂等机制和事后查询。仅在本地保存一个 operation_id 并不能自动让远端幂等。下游不支持去重时，应先查询实际状态；无法查证则暂停并请求复核。AWS 的幂等 API 文章解释了重试为什么需要表达同一调用意图。参考：安全重试。

代码编辑也有类似问题。若进程在写文件之后、保存 checkpoint 之前崩溃，恢复时不能假设文件仍然没改。需要对比文件摘要或版本差异，让持久状态与现实重新对齐。数据库事务保护的是它覆盖的资源，并不会神奇地同时保护 shell、远端 API 和工作区。

5. 如何划分模块，为什么不是一个巨大的 Prompt

一种适合起步的划分是：输入与身份层、任务状态层、上下文构建器、模型适配器、工具注册与权限层、执行器、证据存储、验证器、成本与追踪。模块不是越多越好，而是要把可独立测试的责任分开。例如模型供应商变化不应要求重写授权规则，摘要算法变化不应改变远端操作是否允许。

以运维场景类比：告警进入系统后，先固定对象和时间范围，再只读采集证据，提出假设，执行有范围限制的诊断，最后验证恢复指标。如果允许修复，还需要明确变更窗口、回滚方式和终止条件。“告警消失”不一定代表故障消失，也可能是监控失效。这说明完成条件属于业务语义，不能只看工具 exit code。

从 Prompt 到 Context 再到 Harness，增加的不是几层时髦术语，而是治理范围：Prompt 管这次如何表达任务；Context 管这次看到哪些信息；运行时管理多步过程中的状态、行动和失败。更大的治理范围带来更强控制，也带来更多实现和运维成本。

6. 固定工作流、手写循环与图框架怎样选择

若任务是“取一份已知表格，按固定规则校验，生成报告”，固定工作流往往更容易测试；模型可以只承担其中一个难以规则化的步骤。若需要根据代码库反馈决定下一步查哪里，允许模型动态选择动作更合理，但仍应限制动作集合和预算。

手写循环适合控制流简单的原型；当恢复、分支、并行、人工复核与状态合并成为主要问题，显式图结构可能值得引入。LangGraph 的基本抽象是状态、节点和边，节点并不必须调用模型。选它的理由应是状态与流程复杂度，而不是“项目用了 Agent”。参考：Graph API。

不要用框架数量证明架构先进。先测一个最小基线：在相同任务集、相同模型、相同预算下，新增编排是否减少故障恢复时间、提高成功率，还是仅增加延迟。如果不需要跨中断恢复，先引入整套持久化与分布式任务系统可能得不偿失。

7. 比较产品之前先固定比较对象

“DeepSeek harness”和“pi”缺少仓库、文章或版本定位时，不能据名字写一张看似确定的技术对比表。前者可能是模型配套运行环境或某篇文章的具体实现，后者也可能指不同项目。正确研究动作是先取得源链接、版本或 commit，然后区分公开可验证事实、实测观察与自己的设计推断。

比较 Claude Code、Codex 或自己的项目，也不应停留在“一个擅长推理，一个擅长编码”的泛化判断。可以固定十个真实任务，比较上下文构建、工作区隔离、工具权限、失败恢复、验证证据、可扩展接口和总成本。结论必须带模型、版本、任务分布与评测方法。这里提供比较方法，不伪造用户自己的实现差异。

8. 一个能检验你是否理解运行时的实验

搭建一个只有 read_file、apply_patch、run_tests 三个工具的原型，用模拟模型先完成控制流。给测试工具注入四种行为：成功、确定失败、超时且未执行、超时但已完成。让系统在最后两种情况下给出不同恢复路径。之后再接入模型，才能知道失败来自推理还是宿主逻辑。

  1. 记录每次状态迁移、工具参数摘要、耗时、证据引用和停止原因。敏感内容应脱敏，不能为了可观测性把所有秘密写进日志。
  2. 定义任务成功率、越权请求拦截率、未知结果被误判率、恢复后重复副作用次数和每个成功任务的总成本。token 少不等于系统便宜，失败重试也要计入。
  3. 对自己的项目回答：哪一个模块由你实现？遇到的最难故障是哪条状态迁移？如果重做，哪个复杂度有数据支持可以删除？没有真实项目证据时，把这些保留为实践记录问题，不编造经历。
