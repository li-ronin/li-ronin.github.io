介绍第二个项目（RAG）

介绍 RAG 项目时，最重要的是说清楚“哪些人遇到什么信息问题，系统怎样从资料里找到依据并回答”。RAG 是 Retrieval-Augmented Generation，即先检索资料，再把资料和问题交给生成模型。它不是把所有文件训练进模型，也不是只要接上向量数据库就完成了项目。

下面是一个假设的内部文档问答项目，用来说明应该展开哪些内容，不代表作者已经做过。

从真实问题开始

用户想知道“某接口在版本 2.0 是否支持取消”，但答案分散在接口文档和变更记录中。系统需要找到正确版本的资料，指出结论来自哪一段，而不是把旧版本描述混进回答。这个具体需求会影响后面的数据处理：文档必须保留版本号和来源。

说明完整流程

先收集有权使用的文档，去掉目录噪声，保留标题、正文和版本信息；将长文档拆成适合检索的小段；用户提问后，从这些段落里找相关材料，过滤无权访问或版本不匹配的内容，再给模型生成答案。展示给用户时带上来源，让用户能回到原文核对。

不要只罗列“用了 embedding、reranker、LLM”。应解释它们分别负责什么：embedding 把文本转成便于比较的数值表示；初步检索找候选段落；reranker 对候选与问题的相关性重新打分；生成模型组织答案。每个环节都有可能失败，因此需要分开评价。

个人贡献怎样说清楚

“我们做了知识库”不说明自己做了什么。可以按实际记录说明负责的数据清洗规则、检索接口、权限过滤或评测工具，并指出具体代码与测试。若只是参与其中一部分，应明确边界，不把整个团队成果都写成个人成果。

最终应提供一条能检查的因果链：发现了什么失败，例如版本混淆；修改了什么，例如增加版本过滤；如何验证，例如专门准备不同版本冲突的问题；结果怎样。没有真实数据时不要编造提升百分比。理解这条链，才能从一个工具清单看到一个真正解决问题的系统。

你平时自己还用你的coding agent么？

“平时是否继续使用自己的 Agent”是在确认它离开演示之后是否仍然有用。这个问题需要作者本人提供真实情况，不能根据项目介绍推断一直在用。如果只做过课程实验，也可以如实说实验结束后没有持续使用，再说明原因。

为什么持续使用能够暴露不同问题

演示通常只有几条精心选过的任务，输入清晰、环境正常、上下文很短。日常使用会遇到需求反复修改、代码库变更、工具超时和错误日志特别长等情况。这些问题未必能通过一次成功截图发现。

例如一个假设的 Coding Agent，首次修复简单语法错误很顺利，但使用者第二天说“在昨天版本上增加功能”时，它没有恢复修改过的文件状态，又按旧代码给建议。这个失败反映的是会话与仓库状态不一致，不一定是模型不会写代码。修复方向可能是每次继续任务前检查当前提交和文件差异，而不是单纯换更大的模型。

怎样记录真实使用

给每次任务保留简短记录：任务类型、是否完成、人工介入了哪里、失败原因、耗时和成本。把“用过”进一步分成完全自动完成、人工修正后完成、放弃。只统计最终完成会掩盖大量人工补救。

还可以记录自己为什么不用它：启动麻烦、等待太久、修改范围不可控、无法访问测试环境，或者现成工具更好。这些都是真实产品问题，不需要把它们包装成成功。

怎样据此改进

优先找反复出现而且影响大的失败。例如十次中六次卡在构建环境，先提供可靠构建脚本；若主要问题是错误理解需求，先加强需求确认和验收条件。一次只改一个主要因素，再用之前失败的任务回归，才更容易判断修改是否有效。

个人经历的答案应来自这些记录，而不是套用“我每天都在用，效率提升很多”。即使结果是“暂时不继续用”，只要能说明原因、证据和后续取舍，也比没有依据的宣传更有学习价值。

个人基于什么出发点，要做这个项目？

相关原问题：

为什么要做这个项目，出发点是什么？

选择项目应当先有一个想解决的问题，再判断哪种技术适合，而不是先决定“我要用 GraphRAG”或“我要做微调”，然后寻找能套进去的理由。这里涉及作者的实际动机，不能代写成已经发生的个人经历；下面提供两类项目的推导示例。

RAG 项目的出发点

假设资料经常更新，而使用者需要知道答案对应哪份最新文档。单靠模型原有知识不容易保证时效与出处，因此可以尝试检索资料再回答。先用关键词搜索建立一个简单基线：如果已经能准确找到答案，就不必立即搭建复杂图谱。

如果失败问题是“同一个概念有很多说法”，可以尝试语义检索；如果问题需要沿多个实体关系找证据，再考虑是否需要图结构。每增加一种技术，都要指出它解决了哪种已观察到的问题，而不是只说“效果更好”。

模型训练项目的出发点

另一个假设任务是把格式混乱的短文本转换成固定字段。先尝试明确提示词和少量示例。如果准确性仍不足，且有足够一致、合法可用的标注数据，才考虑微调。微调让模型学习特定输出习惯，但不能自动修复错误标签，也不一定适合频繁变化的事实知识。

训练项目要明确学习目标：想理解训练流程，还是想得到可部署的模型？如果主要目的是学习，较小规模的可复现实验也有价值，不需要声称达到商业效果。如果目标是部署，则要考虑延迟、硬件、维护和模型许可。

如何避免事后编理由

把最初的需求、尝试过的简单方案、失败案例和选型记录保存下来。最终说明为什么没有选另一条路径，以及自己的时间或资源限制。技术选择往往有多个可行答案，关键是理由与实际条件一致。

一个完整解释可以是“需要解决 X；简单方案在 Y 上失败；选择 Z 是因为它能处理 Y；通过测试 W 检查是否真的改善”。其中 X、Y、Z、W 必须来自自己的项目事实，而不是为了显得高级而补上的故事。

选一个你参与最深的 Agent 项目，讲清楚它的用途和你的工作。

问题来源：阿星不是程序员

用途和个人工作是两件事，应该分开讲。用途说明用户为什么需要这个系统；个人工作说明自己实现、验证或维护了哪些部分。不要用“我做了多 Agent、RAG 和工具调用”代替用途，因为这些是实现手段，读者还不知道它最后帮助谁完成了什么。

一个仅用于理解结构的例子

假设项目帮助开发者排查编译失败：输入是仓库位置和构建错误，输出是一个修改补丁与验证日志。系统先读取报错涉及的代码，再提出修改，执行构建，直到通过或达到限制。这里可以清楚地指出自动化范围：只修改工作副本，不自动合并到主分支；遇到依赖安装等额外动作时暂停。

怎样界定个人工作

如果自己负责工具执行部分，就展开说明如何限制可读取路径、怎样运行构建、如何处理超时、如何把日志送回模型。若模型选择和前端由别人负责，应直接说明，而不是把团队架构全部算作个人完成。

可以选一条真实任务，沿输入到输出讲一次：错误是什么，程序读了哪些文件，模型返回什么数据，执行器做了什么，最后用哪个测试确认结果。读者因此能看出系统确实运行过，而不是只有架构图。

什么证据最有用

代码提交、可复现用例、运行日志和设计记录能够支持具体说法。比如“我实现了超时取消”应能展示超时后子进程是否退出、资源是否释放，以及任务状态是否正确更新。只展示最终文本回答，无法证明这些工程行为。

现有材料没有作者真实 Agent 项目的实施记录，因此这里不应生成一段第一人称项目自述。真正归档时，可以保留原问题和上述分析，再用真实经历替换示例。要学会的是把一个项目从“用了哪些热门组件”说明到“接收什么、执行什么、交付什么、自己负责什么、用什么证据验证”。

项目里最难处理的问题是什么，你具体改了哪里？

问题来源：阿星不是程序员

“最难的问题”不一定是代码最长的模块，而是导致项目无法达到目标、又不能靠直接套用现成做法解决的问题。这个问题必须建立在真实经历上，不能替作者虚构事故。下面用假设案例说明怎样把技术细节讲清楚。

假设 Agent 在网络超时后重复创建工单。表面看是“请求失败了，再重试一次”；实际第一次请求可能已经成功，只是响应没有传回客户端。第二次请求又创建了一张工单。这说明没有收到成功响应，不等于操作没有发生。

怎样定位原因

查看请求编号、服务端记录与时间线，确认两次请求对应同一个业务任务，而不是用户真的提交了两次。区分连接前失败、发送后超时、服务端处理后响应丢失等情况。如果不区分，可能把所有错误都归为“模型不稳定”。

具体修改应该是什么

给一次业务操作分配稳定的幂等键，例如同一任务的“创建工单”步骤始终使用同一个键。幂等的意思是重复提交同一操作不会产生多份业务结果。接收端需要识别这个键并返回已有结果；客户端仅仅生成一个随机编号而接收端不使用它，并不能避免重复。

如果外部服务不支持幂等，还要通过可查询的业务编号确认是否已创建，或将不确定状态交给人处理。不能靠一句“保证 exactly-once”掩盖无法跨两个系统原子提交的事实。

如何证明问题解决

用故障注入重现“服务端成功但客户端超时”，再验证重试不会增加第二张工单。保留前后日志，而不只是测试正常路径。与此同时检查幂等键是否会错误地合并两个不同的任务。

真实回答应替换为自己的问题，并保留上述逻辑：症状、原因、修改位置、关键机制、验证方式。难点的价值在于展示因果推理和验证，不在于堆叠术语。若没有发生过此类问题，不应将这个示例写成个人经历。

如果现在重新做这个 Agent，你会优先重构哪一部分？

问题来源：阿星不是程序员

重新做 Agent 时，不应该先决定“换框架”或“改成多 Agent”。应该先找出目前最影响正确性、维护成本或完成时间的部分，再判断是局部修补还是需要改变结构。没有项目运行数据，就不能断言某一层一定最值得重构。

从失败记录得到优先级

假设有三类问题：日志太长导致模型遗漏需求；执行中断后无法继续；界面不够美观。若前两类经常让任务失败，通常应优先处理它们。但如果系统只是一次性短任务，根本没有恢复需求，就没有必要为未来假想场景搭建复杂状态系统。

可以给每类问题记录出现频率、影响范围、修复成本与风险。优先项应当能用一句具体的话说明，例如“把任务状态从拼接聊天文本改为单独存储，避免恢复时不知道哪些文件已改过”，而不是“提升整体架构能力”。

用状态混乱作为示例

如果计划、日志、用户需求和工具结果都混在一个长字符串中，程序很难判断任务到底完成了哪一步。可以增加明确字段：任务编号、当前步骤、已完成步骤、修改文件、待确认事项和最后一次工具执行结果。聊天文本仍然保留，但程序不再只能猜文字来恢复任务。

这也不是说把所有东西都结构化就最好。自然语言适合保存开放式说明，结构化字段适合保存必须精确判断的事实，例如操作是否已经提交。两者要分工。

怎样控制重构风险

先保存当前行为的测试，选择一条任务路径迁移，比较新旧实现的结果。确认没有破坏已支持功能后，再扩大范围。保留回退办法，不在一次改动中同时更换模型、工具协议、存储和提示词，否则出现退化难以判断原因。

重构完成的标准也应具体：恢复测试能通过、重复执行减少、调试时间缩短，而不是代码文件变多或使用了新框架。个人项目的真实答案应引用自己的失败与测试记录，上述仅是决策方法。

相比别人的优势是什么？

相关原问题：

希望从这学到什么？

相对优势不是一句“学习能力强”，而是自己能在哪类工作上提供可证明的帮助；希望学到什么也不是“接触先进技术”，而是当前能力与目标工作之间还缺哪一段。这里需要本人经历，不应由别人替你生成不存在的成绩。

把优势变成具体能力

例如熟悉 C++ 并不自动等于擅长 Agent 开发，但它可能帮助理解进程、线程、内存和性能测试。当 Agent 的工具执行卡住时，能判断是子进程未退出、输出管道阻塞，还是模型没有返回，就比只会改提示词更有帮助。这个例子说明的是能力迁移方式，不是在断言作者已完成过这类项目。

同样，熟悉模型算法的人可能更擅长分析数据与评测，却不一定熟悉生产系统部署。不同优势对应不同任务，不能脱离岗位笼统比较“比别人强”。

用什么支持说法

选择一两件真实做过的事，说明问题、自己的具体动作和可检查的结果。若说擅长定位问题，可以展示如何从错误日志缩小范围、怎样设计最小复现、如何验证修复。结果不一定必须是漂亮的百分比；一个能够稳定重现并解决的故障也有价值。

学习目标怎样写得具体

先指出目前能独立做什么，再指出缺少的能力。例如能编写测试脚本，但还不熟悉如何设计真实业务评测；能阅读单个工具实现，但还没有处理多用户权限与任务恢复。这比说“想了解完整链路”更明确。

随后说明希望通过什么工作补齐：参与一次从失败案例设计评测、实现修复、上线观察的过程，或负责一个有明确输入输出的模块。不要把“希望学到”写成对团队必然提供培养、晋升或资源的承诺。

这类问题可以作为个人反思记录，但公开博客中应区分通用分析与个人陈述。只有确实属于自己的经历和目标，才用第一人称填写。

在AI发展这么快的时代，您认为对业务最大的赋能的点在哪？

相关原问题：

随着基模的快速迭代，您认为Agent还有必要么？（回了一个好问题）

AI 对业务的价值，首先要落在某一项具体工作上。比如“客服更智能”还不够，需要进一步问：是减少查资料时间、减少漏答，还是让用户更快完成申请？没有具体目标，很容易把生成文本的速度当作业务收益。

怎样分析一个场景

假设工作人员每天需要查找政策条款。AI 可以帮助找相关材料并整理解释，但应同时检查答案是否可靠、政策是否最新、是否减少了人工核对时间。如果工作人员必须花更长时间检查错误答案，虽然模型回复很快，总体工作反而可能变慢。

可以把收益拆成完成时间、结果质量、可处理任务范围和总成本。对不可接受的错误，例如越权泄露资料，不应简单用平均节省时间抵消。

基础模型变强后，Agent 是否还有必要

先明确两者不是互斥产品。基础模型负责根据输入生成文本或工具调用数据；Agent 应用还需要把实际资料提供给模型、执行外部操作、管理权限、保存任务进度并验证结果。模型能力提高，可能减少规划提示、重试和复杂编排，但它并不自动拥有公司数据库权限，也不会让付款、发信等外部动作不再需要程序执行。

另一方面，不能据此说所有复杂 Agent 设计永远必要。过去要分五步处理的问题，新模型也许一次就能正确完成；过去为弥补能力不足设计的多个子 Agent，也可能变成额外成本。应该持续比较更简单的方案，删除已经不再提供收益的步骤。

如何把问题问得更有价值

与其只问“Agent 会不会消失”，可以问“在你们的业务里，基模变强后哪些人工或程序步骤已经减少，哪些权限、验证和系统接入工作仍不可省？”这样讨论的是具体变化，而不是押一个宏观结论。

最终结论应是有条件的：模型与系统设计共同决定效果，某些编排会被简化，但外部系统接入、授权与结果检查仍须由实际应用承担。每个场景需要用任务和数据重新验证，而不是把 Agent 当作必须保留的标签。
