如何防止大模型生成的幻觉？

不能保证彻底消除幻觉。这里的幻觉指回答听起来合理，却没有事实依据或不符合给定材料，例如编造不存在的 API、论文、报销金额。要做的是减少它出现的机会，并在使用结果前发现它。

先定位错误来自哪一步

假设问“公司出差住宿上限是多少”，模型回答“500 元”。可能是没有拿到制度，拿到了旧制度，检索到了别的城市标准，或者材料明明写 400 元而模型读错。四种错误需要不同处理，不能都靠一句“请不要胡说”解决。

可以按以下方式设计一个文档问答系统，数字是教学示例：先询问或确定地区、人员类别和生效日期；检索用户有权访问的制度；把相关段落及版本号送给模型；要求回答中的金额附具体依据；没有找到就说明缺少哪项材料。这样模型不必仅凭训练时的记忆猜当前公司的规则。

不同措施分别解决什么

检索增强解决“知识没在当前输入里”的问题，但错误文档仍会产生错误答案。工具计算解决“需要精确计算或查询”的问题，例如金额求和交给程序，不能仅要求模型心算。结构化输出可以约束字段格式，却不能证明字段值真实。降低随机性可以让回答更稳定，但稳定地给错答案仍是错误。微调可以改善领域表达和行为，也不能代替及时更新的事实来源。

重要结论要单独核验。金额应与原文数值和适用条件一起核对；代码应检查 API 是否存在并运行测试；引用必须真的支持它前面的那句话。请另一个模型审查可以辅助发现问题，但两个模型可能共同犯错，尤其是审查者没有看到原始证据时。

怎样知道措施有用

准备三类问题：材料能回答、材料无法回答、材料互相冲突。分别统计正确回答比例、无依据仍作答比例、该回答却拒答的比例。只统计“回答中有引用”会高估效果，因为引用可以是无关的。还要记下错误发生在检索、材料解释还是生成阶段，针对性改。

例如十道无依据问题中，旧系统编造了八次，新系统只编造一次，这是进步；但若十道有依据问题中新系统也拒答九次，就不能宣布整体成功。准确性与覆盖率必须同时观察。真正可靠的做法不是让模型宣称“我有信心”，而是让关键结论能够回到可检查的材料、计算或测试结果。

追问为什么需要这么高的成本？

不能仅凭“写 1,000 行代码”准确计算 Token 或费用。模型可能一次写出代码，也可能先读十几个文件、修改多轮、运行测试后重写；最终留下的 1,000 行只占整个过程中一部分输出。

首先数的是什么

Token 是分词后的计费单位，不能固定换算成代码行。长标识符、注释、不同语言和空格都会影响数量。一般要分别累计每次请求的输入 Token 和输出 Token；如果服务区分缓存输入、缓存写入或其他费用，也要分别统计。

例如第一轮输入需求和规则，第二轮又带上源码与测试结果，第三轮再带上新的修改信息。即使用户只说了一句话，整个任务的累计输入也可能很大。缓存可能降低部分重复输入费用，但是否命中、如何计费要看实际服务，不能把“重复内容”自动视为免费。

一次明确的示例计算

下面数字完全是假设，用来解释算法，不是任何厂商当前价格：

累计普通输入：60,000 Token
累计缓存输入：140,000 Token
累计输出：15,000 Token
假设每百万价格：普通输入 10 元，缓存输入 2 元，输出 30 元
费用 = 0.06×10 + 0.14×2 + 0.015×30 = 1.33 元

如果还有按次收费的搜索、独立沙箱运行费或存储费，应另加，避免与 Token 费混算。若价格以美元标注，就先按美元算，不要默默换成人民币。

为什么同样代码量可能很贵

常见原因有：反复发送大文件和长日志；模型在失败后多次重试；多个子 Agent 重复调查同样内容；使用价格更高的模型；输出大量最终未采用的代码；压缩摘要本身也消耗请求。高成本不一定合理，需要用日志解释，而不是说“因为模型很强”。

可以按任务阶段统计：调查、实现、验证、压缩各花多少；按调用记录输入、输出、缓存命中、持续时间和结果。这样才能知道该优化哪一部分。例如若 70% 输入来自重复日志，就优先缩短日志，而不是盲目换一个便宜但错误更多的模型。

“底座是哪个、百万 Token 多少钱”怎样回答

这两项必须从真实项目配置、API 返回或账单中填写：模型完整标识、供应渠道、核对日期、普通输入价、缓存价、输出价。本文没有该项目的配置和账单，因此不能代填一个看似具体的型号和价格。

更有意义的成本指标是“完成一个符合要求且验证通过的任务花多少钱”，并同时报告成功率。一次失败只花 0.1 元不一定比一次成功花 1 元划算。可以拿固定的一组任务运行多次，用实际 usage 字段求平均和高分位成本，给预算留出失败重试空间。

有没有进行评测，评测指标是什么？

有没有做过评测、采用什么指标，首先是项目事实，不能在缺少记录时替作者回答“做过，准确率多少”。但“怎么设计评测”可以从目标开始推导：你希望模型完成什么任务，就要提供能检验这个任务的输入、期望结果和评分规则。

用三种目标区分指标

如果任务是把文本分成“投诉、咨询、其他”，可以统计分类正确率，并检查每类的精确率与召回率。精确率回答“判成投诉的里面有多少真投诉”，召回率回答“所有真投诉里找出了多少”。如果绝大多数样本都不是投诉，只看总体正确率可能掩盖漏检。

如果任务是生成代码，字符串和参考答案不一样不一定错，应运行编译和测试，统计解决了多少任务，并检查是否改坏已有功能。如果任务是依据文档回答问题，则要分别判断答案是否正确、引用是否支持答案、没有依据时是否拒绝乱答。不能把一种指标套在所有任务上。

评测数据怎样准备

把训练、调参和最终测试使用的数据分开。训练集用来更新参数，验证集用于选择设置，测试集留到方案确定后评价。不能反复看测试集错误并据此修改，然后还把它当作完全没见过的新任务。相同或近重复的问题还可能跨集合泄漏，需要按文档、用户或时间分组，而非只随机分行。

先做一个不用新方法的基线，例如原始模型或简单检索。用同一批任务比较，保证提示词、生成限制等条件可追溯。否则不知道提升来自训练、提示词变化，还是测试集变简单。

一份可信结果长什么样

假设一个示例测试集有 100 个任务，新版本通过 82 个，基线通过 78 个。除了“多了四个”，还应检查哪些新增通过、哪些原本通过却退化，以及样本数是否足够支持稳定结论。若一次输出存在随机性，应在合理预算内重复测试并报告波动。

评测记录至少保留任务版本、模型版本、评分规则、原始输出和失败分类。人工评分也要给标准，例如“引用正确但结论超出证据”如何扣分。最终能够回答的不是笼统的“模型很好”，而是“在这类任务、这些条件和这套检查方法下，表现如何，还有什么缺陷”。

你会用什么标准判断一个 Agent 已经具备企业使用的条件？

问题来源：阿星不是程序员

“企业可用”不是一个统一分数，而是系统在明确业务范围内，能够以可接受的风险、成本和速度完成任务。先问它被允许做什么。例如只生成内部工单草稿，与自动修改生产数据库，要求完全不同。后者一旦出错可能影响真实业务，不能因为前者演示成功就一起开放。

先定义可检查的业务成功

假设 Agent 帮助处理内部技术问题。成功不只是“回复了一段话”，而是答案有依据、没有泄露其他部门的数据，必要时能把问题交给人。对每个典型任务写验收条件，再统计成功率、需要人工接管的比例和错误类型。

必须检查的不只有回答质量

权限方面，用户 A 不能通过换一种提问读取用户 B 的资料；写操作必须检查身份、资源范围和授权。稳定性方面，模型超时、工具失败或服务重启后，任务不能悄悄丢失，也不能重复执行已经发生的付款或发信。资源方面，应限制总执行时间、模型调用次数、并发量和费用，防止单个任务长时间占用系统。

还需要能追查问题：保存必要的调用记录、工具参数、结果和版本信息，并对敏感内容做适当保护。保存日志不是把所有用户数据永远保留，而是让错误能够定位，同时遵守数据保留要求。

怎样验证而不是只列清单

用正常任务和故障任务分别测试。例如主动让搜索超时、返回空结果、撤销一个文档权限、让执行器在写入后中断，再观察系统是否做出正确处理。对高风险操作先采用“只建议、不执行”，通过真实业务验证后再逐步扩大权限。

上线初期可以只给少量用户，观察任务失败率、耗时和人工介入。这里“小范围发布”是为了在错误影响有限时发现问题，不是替代上线前测试。

没有必要追求所有任务都全自动。一个能可靠地识别不确定情况并交给人的系统，可能比一个永远自信给结论的系统更适合企业使用。评价时应同时说明适用边界：哪些任务已经验证，哪些尚未开放，发生故障时由谁负责恢复。

让 AI 参与性能测试时，你怎样设计 Prompt 和验证方案？

问题来源：阿星不是程序员

让 AI 参与性能测试时，适合让它帮助列测试维度、生成脚本和分析已有数据；不能让它凭代码猜一个速度提升百分比，再把猜测当作测试结论。首先需要区分两件事：程序运行是否正确，以及正确的程序运行得多快。精度或功能错误的实现，即使更快，也不能直接当作有效优化。

给 AI 的输入要包含什么

以矩阵计算为例，说明输入形状、数据类型、是否转置、测试设备、基线实现、正确性容差，以及计时范围。下面是任务说明示例：

比较实现 A 与 B，使用同一批输入。
先做结果校验，失败的用例不计算加速比。
分别报告小、中、大形状的耗时分布。
区分首次调用与预热后的调用。
保留原始数据、代码版本、运行命令；不能编造未运行的结果。

若没有这些约束，AI 可能把数据准备算进 A 的时间，却不算进 B，得到没有可比性的结果。

真正执行时检查什么

CPU 微基准要防止编译器把无用计算优化掉，注意计时器与优化选项。GPU/NPU 等异步设备上，主机发出任务后可能立刻返回；只测主机调用的开始结束，测到的可能是提交开销，而不是设备完成时间。应该按所用设备接口采用正确的同步或设备事件计时方式，并明确是否包含同步成本。

进行预热后多次重复，保存每次结果，而不是只挑最快一次。比较中位数和高分位耗时，同时记录异常值与机器状态。不同实现可以交替测试，降低温度、频率或后台负载随时间变化造成的偏差。

AI 的分析怎样验证

例如 A 为 10 ms，B 为 8 ms，加速比是 10/8=1.25 倍；耗时下降是 (10-8)/10=20%，两种说法不是同一个数。让程序根据原始记录计算，而不是只让模型心算汇总。若提升只有 1%，而重复运行的波动达到 5%，不能下确定性结论。

最后回到真实业务：单个算子快了，整体任务也许仍被通信或数据准备限制。性能报告应同时列出测试条件、正确性结果、原始数据和结论适用范围，读者才能复现并判断改进是否对自己的场景有效。

延伸问题

以下是根据外部资料另外整理的问题，不是上面原记录的逐字转录。

如何限制Agent的权限和失控循环？

问题来源：代码随想录

限制 Agent 要同时限制“允许做什么”和“最多做多少”。只在提示词写“不要危险操作、不要无限循环”不够，因为模型可能误解输入，程序也可能遇到重复错误。真正的限制要由执行工具的程序检查。

权限怎样落到程序里

例如只允许读取某个项目目录，程序应当规范化路径并确认目标仍在允许范围内，不能只检查字符串以某个前缀开头；符号链接、相对路径和大小写等也需要按操作系统处理。允许读文件不等于允许执行 shell，允许改工作副本不等于允许推送主分支。

把高风险操作单独列出，例如删除远端记录或发布内容，要求明确授权。工具返回的数据以及网页文字不能自行授予权限。即使模型输出了一个工具调用，执行器也可以拒绝，并把拒绝原因返回模型。

怎样防止反复尝试不停下来

为每个任务设置总时间、模型请求次数、工具执行次数、输出大小和费用预算。计数应覆盖每一次模型请求，包括它只返回无效格式或不调用工具的情况，否则“只数工具调用”的限制可能被空转绕过。

每次准备请求模型前：检查总预算
发起请求后：增加请求计数
准备执行工具前：检查权限与工具预算
连续出现同类失败：停止自动重试，解释原因

这不是让系统遇到一次错误就放弃，而是给错误设置有边界的恢复策略。网络暂时失败可以有限重试；同一参数连续被权限拒绝，重复请求通常没有意义。

怎样证明限制有效

测试一个总是返回错误的工具，确认程序最终会停止；测试超长输出，确认不会占满内存；测试越界路径，确认在执行前拒绝。还应检查超时后子进程真的终止，而不是主任务显示失败但后台仍继续运行。

限制越严格，可完成的任务可能越少，因此需要按场景配置，但不能把方便完成任务作为关闭所有限制的理由。可解释地停止并请求必要信息，通常好过无限尝试或越权成功。

中断恢复后，怎样避免外部操作重复执行？

问题来源：TrustZone

中断恢复后的关键问题是：程序可能不知道外部操作是否已经成功。比如创建工单的请求发出后，服务端已经创建成功，但客户端在保存结果前崩溃。重启后若简单重试，会多建一张工单。保存“任务执行到第几步”还不足以解决这个窗口。

首选稳定的业务操作编号

为同一个业务动作生成一次幂等键，并持久保存。重试时必须使用同一个键，而不是每次新建随机值。若接收端支持该键，它应识别重复请求并返回同一结果。例如任务 T 的“创建工单”步骤始终对应 T:create-ticket:1，而另一个真正独立的创建动作使用不同编号。

幂等不是“客户端不重复发送”，而是即使重复发送，也不会重复产生业务效果。实现必须得到接收端或同一个事务数据库的支持。

如果接收端不支持怎么办

可以查找带有业务编号的已有记录，再决定是否提交，但“先查询再创建”本身也可能在并发时竞争，所以还需唯一约束、锁或接收端其他能力。如果无法可靠确认，就把状态标记为“不确定”，由人核对，而不是强行宣称失败后重做。

对本地数据库操作，可以把业务写入与步骤状态更新放在同一事务里；对另一个服务的远程操作，通常不能只靠本地事务保证两边一起成功。需要依据实际系统能力设计补偿或对账。

恢复程序怎样写

把可重复计算的部分与会改变外部状态的部分分开。读取资料、计算摘要通常可以重新执行；发信、扣款、创建记录必须更谨慎。使用流程框架时，要理解它从哪个边界恢复，不能把“支持持久化”理解为每行代码都精确继续一次。

测试时至少模拟三个位置：请求前中断、服务端成功后响应丢失、结果返回后本地保存失败。检查最终是否只有一份业务结果，以及不确定状态是否正确暴露。正常运行一百次成功，仍不能证明这些故障条件下不会重复。

Text-to-SQL中的Prompt改动如何验证有效？

问题来源：momo

Text-to-SQL 是把自然语言问题转成数据库查询语句。修改 Prompt 是否有效，不能只看生成的 SQL 像不像样子，要看它是否在正确的表、字段、过滤条件和权限范围内得到正确结果。

用一个具体问题拆开检查

用户问“上个月每个地区的已支付订单金额”。正确 SQL 需要知道订单表、地区字段、支付状态字段、金额单位，以及“上个月”按哪个时区计算。若 Prompt 只要求“写合法 SQL”，模型可能查询创建时间而非支付时间，或者把分当成元，语法仍然完全正确。

因此输入应包含相关数据库结构和业务字段说明，而不是无差别塞入全部数据库。加入示例时，示例应覆盖日期边界、关联表、空值和聚合等典型情况；还要明确只允许哪些操作。模型收到“只读”指令不等于数据库就安全，实际连接应使用受限只读权限，并设置查询时间与资源限制。

A/B 比较怎样做

固定同一批未参与 Prompt 编写的问题、同一模型版本和同一数据库快照。旧 Prompt 与新 Prompt 分别生成 SQL，先解析检查语法和允许操作，再在隔离测试库执行。比较结果集合，而不只比较 SQL 字符串：两种不同写法可能返回等价结果。

反过来，一次结果相同也可能是巧合。例如数据里没有未支付订单，漏写支付状态过滤也能碰巧正确。要准备能区分错误写法的测试数据，包括跨月边界、重复关联、无记录地区、NULL 和不同币种。涉及排序的问题还需比较顺序，不只是集合。

指标与归因

记录可执行比例、语义正确比例、危险语句拒绝率、延迟和词元成本。按错误类型拆分：表选择、字段选择、连接条件、日期、聚合、单位。若新 Prompt 只提升简单单表查询，却让多表查询更差，总体平均值可能掩盖问题。

最后人工抽查失败与“看似通过”的样本，并对有随机性的生成进行重复测量。Prompt 是一个待验证的程序输入设计，不是改了措辞就自动有效。只有在独立、能暴露真实错误的数据上提升，才能把改动作为正式方案。

怎样说明实体识别准确率的可信度？

问题来源：momo

实体识别是从文本中找出某类对象及其边界，例如从“张三在上海工作”标出人名“张三”和地点“上海”。说“准确率 95%”之前，必须解释判定单位、测试数据和匹配规则，否则这个数字无法比较。

为什么不能只算每个字对不对

大部分文本字符可能不属于实体。一个系统把所有字符都标成“非实体”，也可能得到很高的字符级准确率，但一个人名都找不到。因此通常更关心实体级 Precision、Recall、F1。

Precision 是预测出的实体中有多少正确；Recall 是真实实体中有多少被找出；F1 是二者的调和平均。教学例子：真实有 10 个实体，系统预测 8 个，其中 6 个边界与类别都正确，则 Precision=6/8=75%，Recall=6/10=60%，F1≈66.7%。这比单说“识别了八个”更清楚。

什么算一个正确实体

严格匹配通常要求起止位置和类别都正确。“北京大学”标成“北京”，即使有重叠，也不能算完整识别正确；把组织标成地点也错。某些业务允许部分重叠或标准名称归一化，应单独报告宽松指标，不能与严格指标混用。嵌套实体、多义简称等情况也要事先定义标注规范。

数据怎样支持可信结论

测试集应来自真实目标场景，且与训练集按来源或时间适当隔离。相同句子换个文件名不能算独立样本。分别报告人名、机构、设备型号等类别，因为大类的好成绩可能掩盖稀少类别的失败。长实体、罕见名称、OCR 错字和新型号也应有专项测试。

标注本身不一定可靠。抽样让两名标注者独立标注，再讨论不一致案例，可发现规范模糊。记录样本数、实体数、数据时间范围和置信区间，不要把几十个样本的小数点后两位当精确事实。

如果使用大模型抽取，还要验证输出能否对齐原文，防止它把简称扩写成文中不存在的实体。能生成合理名称不等于成功识别原文实体。最终应保存错误例子，让别人能够理解数字到底代表哪种能力。

离线效果最优方案怎样迁移到在线服务？

问题来源：momo

离线评测是在提前准备好的数据上测试方案；在线服务面对真实用户、实时流量和不稳定外部系统。离线最优说明它在那组任务上表现最好，不意味着可以直接全量部署。可能存在速度太慢、成本过高、数据分布不同或权限检查缺失等问题。

先把离线实验固定下来

保存模型版本、提示词、检索配置、数据版本和评分规则。否则“最优方案”只是一段无法复现的结果。还要检查是否对测试集调得太多，避免把记住测试样本误认为具备泛化能力。

加入线上才明显的约束

例如一个检索方案离线回答更准确，却每次需要多次模型调用。真实用户可能等不了几十秒，高峰期还会放大排队。需要同时测端到端耗时、吞吐、失败率、单任务成本以及下游限流。

在线数据也可能不同：离线都是完整问题，真实用户却经常说“那上一个呢”。因此应补充多轮、模糊输入、权限变化和空结果等情况。

怎样逐步发布

可以先在不影响用户结果的条件下运行新方案，与现有方案对比，称为影子测试。这里仍要遵守用户数据允许用于何处的限制。接着给少量符合条件的请求使用新方案，观察真实效果；若错误或延迟超过预定阈值，切回原方案。

对照实验应尽量保证两组用户和时间条件可比，不能把周末低流量的新方案与工作日高峰的旧方案简单比较。还要注意平均值掩盖某类用户的退化。

上线后怎样继续判断

保留经过隐私处理的失败分类，定期把新的失败样本加入评测集。固定一部分老任务做回归，防止修好新问题却破坏旧能力。

真正的迁移过程是：可复现实验、加入服务约束、小范围验证、可回退发布、持续观察。重点不是把一个 notebook 包装成接口，而是确认它在真实条件下仍然满足要求。

如何单独衡量规划质量和幻觉问题？

问题来源：雾中列车

规划质量和幻觉是两个不同问题。规划质量关心“步骤能否把任务做成”；幻觉关心“输出的事实是否有依据”。一个计划可以步骤合理，却引用不存在的文件；一个答案也可以事实都正确，却没有完成用户要求。只给整次任务打一个总分，很难定位原因。

怎样检查规划

用“给项目新增接口并补测试”为例，先列出必要条件：理解接口要求、找到相关实现、修改代码、运行测试、检查兼容性。评估计划是否覆盖必要步骤、步骤顺序是否有依赖错误、是否包含允许范围外的动作。

计划不必与参考答案逐字相同。先写测试再实现与先修改再补测试，可能都能完成任务；关键是是否漏掉验证、是否在尚未得到用户确认时执行高风险操作。还应检查执行中发现新情况后，计划是否合理调整，而不是只评最初的一段文字。

怎样检查幻觉

将答案拆成可核对的陈述。例如“测试全部通过”“文件 A 定义了接口 B”“文档要求版本至少为 2.0”。分别查实际测试日志、代码位置和文档证据。找不到依据时要标注不支持；如果依据明确相反，则是错误，而不是仅仅缺少引用。

模型自己给出的信心分数不能代替核对。引用了真实链接也不代表链接支持那句话，需要看对应内容。

怎样隔离两个因素

可以给系统一份固定正确计划，检查执行和事实性；也可以让系统生成计划，但由确定的执行器或人工检查每个步骤是否可行。这样更容易知道失败来自规划、工具执行还是最后总结。

例如计划中明确要求运行测试，工具却超时，最后模型仍说“全部通过”：计划本身未必错，问题在于错误报告了执行结果。反过来，模型诚实报告没有测试，但任务要求验证完成，则主要是任务完成度不足。

把这些类别分开统计，才能针对原因改进，而不是每次失败都只改提示词。
