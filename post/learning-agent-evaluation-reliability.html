1. 先定义成功，才能谈“效果不错”

Agent 的输出可能是一段回答，也可能是一组外部操作。两者的正确性定义不同：回答要有事实依据，代码要通过验证，操作任务则要检查外部世界是否达到目标。不能因为模型说“完成了”，就把任务记为成功。

构造一个教学场景：Agent 从一份申请中提取字段，检查规则，再在测试工单系统创建记录。成功应同时满足字段正确、规则正确、记录存在、没有重复创建，并且没有越权访问。若只检查最后回复是否包含“已创建”，一个完全没有调用工具的模型也可能拿满分。评测器必须能观察真实产物或受控模拟环境。

Anthropic 的 Agent 评测文章强调任务、试验运行与评分器等概念。本文据此进一步设计自己的分层判据，而不把某篇文档中的指标当作所有系统的统一标准。参考：Agent 评测方法。

2. 把结果、过程和安全拆开计分

结果指标回答“做成了吗”：字段匹配、测试通过、工单状态。过程指标回答“怎样做成”：工具次数、重复检索、计划偏离、恢复次数。风险指标回答“代价是什么”：越权访问、错误副作用、敏感数据暴露。这三类可以相关，却不能彼此代替。较短的轨迹不一定更正确，较高的成功率也不能抵消严重的越权行为。

例如 100 个任务中 86 个结果正确，其中 2 个通过绕过审批获得结果。业务验收不能简单写“成功率 86%”。可以分别报告结果正确 86%、合规完成 84%、越权 2%，并把禁止行为作为发布阻断条件。这个阈值应由业务风险决定；本文数字仅为教学示例。

检索任务可以拆为“证据在库中吗—召回了吗—排序进上下文了吗—回答忠实吗”。NER 则需要明确按实体级精确匹配还是字符级计算，并分类型报告精确率、召回率与 F1。若测试集里绝大多数文本没有实体，单看整体准确率可能把什么都不抽取的系统包装得很好。

把定义落实成一次可手算的 NER 实验：采用“实体边界与类型均精确一致才算命中”，标注集中有 12 个实体，系统预测 10 个，其中 8 个正确。于是 TP=8、FP=2、FN=4，精确率为 8/10=0.8，召回率为 8/12≈0.667，F1 为 2TP/(2TP+FP+FN)=16/22≈0.727。若把边界部分重叠也算正确，这组结果就不再可比。应分别记录格式合法率和抽取质量：JSON 全部合法，不代表实体抽对；只删除困难实体可以提高精确率，却降低召回率。

3. 数据集不是随手挑几个能跑通的例子

先按真实失败机制分层采样：正常输入、缺字段、相互矛盾材料、过期信息、工具超时、同名实体、权限不足，以及带恶意指令的外部内容。每个样本保留输入、环境初态、允许动作、预期产物和判定依据。对个人数据使用合成或已获授权的脱敏样本，不把生产秘密复制进公开测试。

调 Prompt 使用开发集，确定方案后再看保留测试集；反复根据测试集改提示，测试集就成了训练信号。比较新旧方案时尽量用相同任务初态，记录模型版本、工具版本和随机设置。对于非确定系统，一个任务只跑一次可能碰巧成功；重复运行能观察稳定性，但多次运行的相关性意味着不能机械把它们视作完全独立样本。

“100 次没有事故”不等于事故概率为零。在相互独立且同分布的简化假设下，零失败的单侧 95% 上界约为 1−0.05^(1/n)。n=100 时约 2.95%。这不是生产风险保证，而是提醒：罕见高损害事件需要专门的对抗样本、权限限制和故障注入，不能只靠普通通过率证明安全。

4. 评分器也要被测试

优先使用可直接验证的条件：JSON Schema、唯一约束、文件摘要、单元测试、目标记录状态。对于事实性和解释质量，可以让模型辅助评分，但要固定评分标准、提供证据，并用人工标注校准。模型评审可能偏爱更长、更自信的文字，因此“由另一个模型判断”并没有消除测量误差。

Text-to-SQL 是一个很好的反例：仅比较 SQL 字符串会错杀语义等价写法；仅检查能执行，又会放过返回错误结果的查询。可以在有针对性的测试数据库上比较结果集、权限和资源约束。数据库内容要包含边界关系，否则错误 JOIN 可能碰巧得到正确结果。PostgreSQL 的 EXPLAIN 用于观察执行计划；EXPLAIN ANALYZE 会实际执行语句，不能把它当成无副作用的只读字符串检查。参考：PostgreSQL EXPLAIN。

给评分器准备“故意错误”的输出：遗漏一个关键约束、引用无关段落、重复创建记录、用旧结果冒充新结果。评分器若不能稳定拒绝这些样本，就不适合为 Agent 的改进背书。幻觉控制也应覆盖无证据、证据矛盾、证据过期三种情况；合理拒答有时比编出完整答案更正确。

一个足以击穿弱 SQL 测试的反例：订单表只有订单 A，金额 100；明细表中 A 对应两条商品。目标是查询订单总金额。直接在订单表 SUM(amount) 得到 100；先 JOIN 明细再 SUM(orders.amount) 会得到 200，因为一对多关联复制了订单行。如果测试数据每单恰好一条明细，两段 SQL 都得到 100，错误查询便会通过。因此至少构造零条、一条、多条明细，重复金额以及 NULL 等边界。也不能随意用 SUM(DISTINCT amount) 修复：两笔不同订单金额同为 100 时，会被错误合并成 100。应先明确聚合粒度，再选择预聚合、存在性判断或适当关联。

5. 成本不是“写一千行代码用了多少Token”

代码行数不能稳定预测 Token：语言、命名、注释、输出格式都影响分词；更大的成本还可能来自反复读取上下文、失败重试和工具返回。应按每次请求记录实际输入与输出 Token，再分别按适用的计费类别汇总，缓存命中、额外工具费用和运行环境费用另算。

C_task = Σ (I_i × P_in + O_i × P_out) / 1,000,000
         + C_tools + C_environment
C_per_success = 总支出 / 合格完成任务数

假设某教学服务的价格为输入每百万 Token 2 美元、输出 8 美元，这不是实际厂商报价。一个任务有 5 轮请求，输入依次为 1000、2000、3000、4000、5000 Token，输出每轮 500。输入费用 15000×2/1000000=0.03 美元，输出费用 2500×8/1000000=0.02 美元，再加工具费用 0.01，总计 0.06。若 100 个这样的任务只有 80 个合格完成，平均成功成本是 6/80=0.075，而不是 0.06。

因此优化目标应是满足质量和风险约束下的成功成本与延迟。盲目压缩上下文可能减少单次费用，却增加错误与重试，最终更贵。把固定工作流、检索裁剪、小模型路由等策略作为可比较变量，而不是先假定模型越小越划算。

6. 结果未知是一种必须保存的状态

考虑创建工单：服务器已经成功写入，但返回包丢失。客户端看到超时，并不能判断“没有创建”。如果直接重试，可能产生第二条记录。把任务状态持久化到 checkpoint 也不够：外部成功与本地落库之间总可能有窗口。

operation_id = stable_id(logical_request)
record(operation_id, "pending")
result = call_service(idempotency_key=operation_id)
if result.confirmed:
    record(operation_id, "succeeded", result.id)
else:
    record(operation_id, "unknown")
    reconcile_with_service_before_retry()

上面是设计伪代码，真实系统需要原子状态迁移和并发控制。幂等键应绑定同一个逻辑请求，重试时复用，而不是每次生成新键。服务端要检查同键不同参数的冲突，并定义保存多久。若服务不支持幂等，也无法查询结果，系统应该停在待核验状态，不应为了让界面显示完成而再提交一次。参考：AWS 幂等 API 设计。

测试需要注入三个断点：请求发出前、远端成功后、本地结果持久化前。预期最终只有一个逻辑产物，并且每个操作都能解释其状态。权限同样必须在执行层检查，不能把模型愿意遵守提示当作安全边界；预算、最大步骤和超时则负责限制失控循环。

7. 从离线最优到可上线，不是一键切换

离线结果证明的是已测分布，不是未知线上流量。可以先影子运行，只观察不产生外部副作用；再对低风险流量逐步放量，监控失败类型、尾延迟、成功成本和人工接管率。需要预先定义回滚条件，以及失败后由谁接管，不能等事故发生再讨论。

性能实验应先固定正确性，再控制输入、并发、机器资源和版本。均值下降但 p99 变差，可能让少数关键用户更痛苦；吞吐增加却因限流重试造成额外费用，也不是纯收益。记录至少一个基线、一个改动、一个消融：例如关闭重排、缩短上下文或取消多 Agent，观察收益究竟来自哪里。

对于规划质量与幻觉，可用不同失败样本分开测：计划步骤完整但事实引用错误，是生成或证据问题；事实都正确却先执行不可逆操作再检查权限，是顺序和安全问题。区分层次，才知道该改检索、规划还是执行器。

8. 把项目表达还原为真实的因果证据

个人项目问题不能由通用文章代答，但可以准备一份可复核记录：原问题是什么，谁受影响，为什么现有方案不足；你负责哪个模块；改动前后采用了同一套什么测试；收益、代价和未解决问题分别是什么。一个诚实的“在这组输入上降低了排队时间，但未验证跨机器效果”，比没有条件的“性能大幅提升”更有信息量。

选型也需要反事实：如果不用 GraphRAG、多 Agent 或自建框架，会发生什么？先建立简单基线，再指出具体失败样本和需要的能力。如果基模升级能解决旧问题，应重新评估原组件，不必为了维护过去的设计保留无效复杂度。Agent 的价值来自把模型能力接到可控环境、状态和验证上，而不是保证所有任务都需要复杂编排。

练习：建立 20 个合成任务，至少 5 个故障或越权案例。给每次运行保存输入版本、轨迹、最终产物、评分依据和成本。先运行简单单 Agent 基线，再只改变一个变量。预期不仅得到一个通过率，还能说清每个失败位于哪个阶段；对结果未知的外部操作，评测应明确失败或待核验，而不是算成功。
