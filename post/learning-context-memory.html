Claude Code上下文是怎么压缩的

相关原问题：

你对 Claude Code 的上下文压缩机制了解多少？

问题来源：阿星不是程序员

Claude Code 的上下文压缩，简单说就是：会话越来越长时，不再把早先所有聊天和工具输出原封不动地交给模型，而是清理部分旧材料、把较早的讨论整理成更短的内容，让任务能够继续。

这里要先区分“上下文”和“模型记忆”。上下文是这一次请求中模型能够利用的输入材料，例如你的需求、源码和命令输出。模型不会因为昨天读过一个文件，就自动永久记住你的仓库。程序下一次要么继续提供相关内容，要么提供摘要，要么让模型通过工具重新读取。

官方能确认到什么程度

截至本文核对时，Claude Code 文档说明：接近限制时会先清理旧工具输出，必要时总结会话；可以使用 /compact 主动压缩并指定关注内容，用 /context 查看空间使用。长期规则可以写入项目指令文件。它没有因此承诺每句话都完整保留，也不能据此断言内部永远采用某个固定阈值、某个摘要模型或“三层压缩”。具体行为应结合所用版本核对。

用一个自己的例子理解压缩

假设之前讨论过 20 轮代码修改，读了几千行日志。真正需要继续解决的是“空数组处理已经修好，但大整数求和溢出”。压缩后可能用类似下面的简短记录表达旧阶段：

目标：修复 sum 的边界问题，不改变公开接口。
已完成：空数组处理；对应测试通过。
当前问题：大整数求和溢出，尚未修复。
证据：保存的失败日志及当前源码路径。
下一步：检查累加变量类型和边界测试。

这是解释压缩思想的示例，不是 Claude Code 内部摘要模板。它比全部对话短，但省掉了早期逐句讨论。后续如果需要某一段精确源码，就应该重新读取，而不能把摘要当成原文件。

为什么压缩后可能“忘了”要求

摘要会选择信息。若“不要改接口”只在很早的一句聊天中出现，摘要没有保留，模型后续就可能看不到。即使保留了，也不能保证模型绝不犯错。所以重要项目约定需要有稳定存放位置，并在修改和测试中验证。压缩保存的是继续工作的必要线索，不是无损备份。

压缩也不等于删除项目文件、撤销修改或清空磁盘上的会话记录。这些是不同操作，不能看到上下文减少就推断文件丢失。

可以怎样亲自观察

在一个可恢复的测试项目中，先提出一个明确约束，运行几轮读文件和测试，然后主动执行 /compact。继续提问或修改，检查约束是否仍可用、关键文件是否重新读取、旧结论是否仍有依据。记录版本和操作过程，不以一次实验推断所有版本。尤其别只问模型“你记得吗”：应给一个会违反该约束的修改机会，观察实际结果和测试。

讲一下动态prompt和静态prompt？

这里的 Prompt 可以理解为“这一次调用模型时，程序提供给模型的全部指令和相关材料”。它不只包含聊天框里用户刚输入的一句话。不同 API 会把内容放在不同角色的消息、工具定义等字段中，但从理解问题的角度，可以先按作用拆开。

以修改 C++ 函数为例拆开看

用户说“给这个函数加上空数组处理”，程序可能发送这些内容：

  • 系统或开发者指令：助手负责什么、如何使用工具、哪些事情不能做。
  • 当前用户需求：增加空数组处理，并且不能改变已有接口。
  • 项目规则：使用 C++17、测试命令是什么、哪些目录不能修改。
  • 可用工具说明：read_file 要哪些参数，返回什么；apply_patch 如何修改文件。
  • 本次相关材料：函数源码、调用者、失败的测试输出。
  • 必要的历史信息：刚才已经尝试过什么，用户后来修正了哪些要求。

“注入”不是特殊的模型算法，只是应用程序把这些内容加入当前请求。例如从磁盘读出项目规则文件，把其文本放入消息，就是一次上下文注入。

哪些必须，哪些不必须

没有一个适合所有任务的固定必填内容清单。若只问“什么是线程池”，无需注入整个仓库；若要修改函数，却不给源码、也不给读取工具，模型便无从确认真实实现。判断原则是：缺了这部分，模型还能正确理解当前任务并遵守限制吗？

当前有效需求、必要的执行限制、要使用的工具说明通常应可见；当前代码和报错按任务提供；与任务无关的旧聊天、全部项目文件、所有 Skill 正文不应默认全部加入。更多内容不等于更好：无关内容会占用长度、增加费用，还可能让模型混淆旧要求和新要求。

需要特别区分“模型应该看见的规则”和“程序必须强制执行的权限”。例如禁止修改仓库外文件可以写入 Prompt，但程序仍应在工具层检查路径。不能因为 Prompt 中有一句禁止，就认为实际权限已经受限。

静态 Prompt 和动态 Prompt 是什么

静态指相对稳定、多个请求可以复用的部分，例如角色说明和通用输出格式；动态指随本轮任务改变的部分，例如本轮问题、刚读出的源码和测试结果。这是内容维护方式的区分，不是两种模型。

一种容易实现的组织方式是：稳定规则放在前部，本轮需求和材料放在后部，材料带来源和时间。所谓静态也不是永久不变，项目切换或规则修改后必须更新。还应明确“用户最新要求优先于过期需求”，但外部文件中的文字不能因此升级为用户授权。

可以用一个小测试检验设计：用户先说“改成返回 0”，随后纠正为“空输入抛异常”。最终输入若仍把前一句当有效需求，就是上下文整理出了问题，而不是模型需要更多历史。

相关原问题：

项目里的上下文压缩是怎样实现的？在什么情况下开始压缩？压缩过程具体做什么？

问题来源：阿星不是程序员

上下文压缩，是为了让下一次模型请求放得下，把不再需要逐字保留的历史内容改成更短的记录。它不是把模型参数压小，也不是把文件压成 ZIP；被压缩的主要是聊天历史、读文件结果、命令输出等输入材料。

下面给出一种可以自己实现的方案，不把它说成任何人的项目实绩。

1. 先计算还剩多少空间

Token 是模型分词器使用的文本单位，一个汉字或一个英文单词不一定恰好对应一个 Token。假设某次配置的总上下文预算是 100,000 Token，预留回答空间 8,000、可能马上返回的工具输出 10,000、安全余量 2,000，那么当前可用输入目标最多约 80,000。这个数字仅用于演示，不是 Claude Code 或 Codex 的固定窗口。

应核对所用 API 对输入、输出、推理 Token 的具体限制，使用对应计数方式。在下一次请求前检查预算，而不是等服务端已经拒绝“输入太长”再补救。工具若可能一次返回几十万行，也要先限制它的输出。

2. 压缩时到底改什么

假设历史包含三轮编译输出，每轮 3,000 行，而目前只有最后一次报错仍未解决。可以把完整输出保存在文件里，在上下文中留下：日志路径、执行命令、退出码、关键报错和源码位置。这样没有销毁原始证据，只是不再每轮把它全部发给模型。

随后把已完成阶段整理为短记录，例如“已为 sum 函数加入空输入检查；普通输入测试通过；当前失败是边界值溢出；不得改变函数签名”。最近正在分析的源码、最新失败测试和当前用户要求继续保留。摘要生成后要检查是否遗漏禁止事项、是否把推测写成结论，再替换相应历史片段。

3. 阈值为什么不能随便定成 80%

如果工具输出长度很不稳定，接近上限才压缩会来不及；如果每轮只读几十行，过早压缩又会频繁付出摘要成本，并可能损失细节。阈值要由模型限制、输出预留、工具返回大小分布和测试表现共同决定。

实际可以记录每轮输入长度、压缩耗时、摘要长度、压缩后任务是否继续成功。用同一批长任务比较不同阈值，而不是只比较节省多少 Token。若输入变短了，但模型反复重读文件或忘记约束，整体可能更贵、更慢。

4. 一个最小执行顺序

准备下一轮材料 → 计算预算 → 先裁剪可重新读取的大输出 → 必要时总结旧阶段 → 检查必留字段 → 再次计数 → 发送请求。如果仍超限，应该进一步缩小读取范围或报告材料过大，而不是不停生成摘要。项目中真实使用的窗口和阈值，应从配置和调用日志读取，不能由本文代填。

为什么要采用三层压缩策略，每一层压缩的内容一致么？分别在什么条件在触发？

采用三层压缩，通常是为了先做损失小、成本低的处理，不够时再处理更重要的历史。三层并不是 Agent 的统一标准，也不是只要分三层就一定好。下面用一个明确的设计例子解释“为什么分层、每层处理什么、什么时候触发”。

第一层：缩短过长的单次工具结果

一次编译输出 5,000 行，大部分是重复警告。如果把它原样加入每次请求，当前问题还没有分析，空间已经被日志占满。程序可以保留第一条真实错误、相关位置、退出码和完整日志文件路径，重复行只保留计数。

这层处理的是单次返回材料，而不是整个会话。可以在工具返回时，发现输出超过单次限制便触发，不必等总窗口接近上限。适合明确可机械处理的内容：相同行去重、超长列表分页。不能不看结构就截取前 100 行，因为真正的失败原因可能在末尾。

第二层：移出不再需要逐字读取的旧材料

模型已经根据 sum.cpp 的旧版本完成修改，旧源码全文通常不需要继续每轮发送。可以替换成“旧版本见某文件或提交；本阶段修改了空输入分支；当前源码必须重新读取”。旧的成功测试日志也可以缩成测试名、版本和结果。

这层处理旧工具输出、旧版本内容，触发条件可以是总预算逼近阈值，且某些材料已不再是当前分析对象。它不同于第一层：第一层处理刚返回的巨大输出，第二层判断哪些历史材料已经过时。保留可追溯路径很重要，否则后续发现结论有误时找不到原证据。

第三层：总结较早的对话阶段

前两层仍不够时，再把较早讨论总结成任务状态：用户目标、有效约束、做过的修改、已验证结果、未解决问题和下一步。最近几轮仍保留详细内容。摘要可以由模型生成，但生成结果需要检查，尤其不能漏掉否定词，例如“不要修改公开接口”。

这层处理语义信息，风险最高：删日志行容易检查，漏掉一次用户纠正却可能让任务方向改变。因此只有确实需要时再做，并把最新用户要求和权限限制单独保存，不依赖摘要模型记住。

三层内容是否一致

不一致，但可能有重叠。同一段日志先经过第一层去重，后来作为旧材料被第二层移出；第三层只保留它所支持的结论。需要保存来源关系，避免第三层再次“总结摘要”后逐渐把不确定结论变成事实。

比较设计是否值得使用，应至少运行两组任务：长日志任务、长时间多次修改需求的任务。检查最后需求是否满足、是否重读过多材料、总费用和耗时是多少。若一个简单任务只靠第一层就足够，就没有理由强制跑完三层。

如果模型因为压缩过度，效果不理想，你是怎么发现的，怎么处理这种异常？

发现压缩过度，不能只靠模型说“我忘了”。应该看压缩前后是否丢失了完成任务需要的信息，以及这种丢失是否造成可观察的错误。

先看一个具体故障

用户要求：“修复空数组问题，但不要改变 sum 的函数签名。”压缩后摘要只剩“修复 sum”。下一轮模型把函数改成接受另一种参数。修改本身可能编译通过，但违反了用户要求。这是一个可以检测的压缩失败：原始需求有“签名不变”，摘要没有，最终差异又改变了接口。

可以在程序里把“签名不变”保存成独立约束，不让它仅存在于摘要中。修改后检查接口声明、编译调用方测试，就能发现问题。不应把所有验证都交给生成摘要的同一个模型自评。

哪些信号值得记录

第一类是信息保留检查：最新目标、禁止事项、未完成步骤、关键文件与版本是否仍然存在。第二类是行为异常：突然重做已完成步骤、反复询问已给出的信息、把失败测试说成成功、使用过期路径。第三类是结果检查：原来通过的测试重新失败，或需求检查项不满足。

但这些信号只是线索。模型本身也可能犯错，仓库也可能被别人修改。不能看到压缩后出错就断言一定是压缩造成的。

怎么确认原因

保存压缩前的原始会话和压缩后的输入，取同一个任务节点，分别用完整材料和压缩材料继续运行。保持模型版本、代码起点、工具配置一致，并重复多次，比较约束遗漏率和任务成功率。这样是在做对照实验。单次结果不能证明因果，因为模型输出可能具有随机性。

还可以检查“信息在不在”：若关键限制在摘要中消失，证据更直接；若限制仍在，则应继续调查模型理解或执行检查。调试时记录摘要生成版本、裁剪策略和相关调用编号，才能知道是哪一次处理删错了内容。

出错之后怎么恢复

先停止继续写入，避免错误扩大；从外部保存的原始记录恢复相关片段，不必把全部历史塞回去；重新读取当前文件，判断哪些错误修改需要撤销；把恢复的约束与当前事实加入新请求，重新规划和验证。

对于已经执行的外部操作，恢复聊天历史不等于恢复现实。例如已经发出的通知不能靠回滚摘要撤回。文件修改也要检查之后是否有人工改动，不能直接覆盖。修复完成后增加一个回归案例：在包含那句关键限制的会话中强制触发压缩，验证限制仍被保留且结果满足。这样才算修复机制，而不是只补救一次。

如果让agent需要对原来的任务上进一步修改，比如新加一个功能，你这个系统是怎么做的？需要重新注入哪些信息？（我理解是恢复会话？）

可以恢复会话，但“恢复会话”和“继续修改现有项目”不是一回事。恢复会话让系统找回之前的讨论和任务记录；继续开发还需要重新检查磁盘上的代码、测试结果和用户的新要求，因为这些内容可能已经变化。

以先实现登录、再增加验证码为例

昨天完成登录功能，今天用户说“再加验证码”。系统不应该重新从零编写登录模块，也不应该相信昨天的摘要就是现在的代码。它需要完成四件事。

  1. 找回任务背景：已有登录流程是什么、当时哪些需求已完成、哪些限制仍然有效。
  2. 读取当前项目：检查分支、未提交改动、相关文件和测试。昨天的文件位置可以帮助定位，但真正修改前应读取当前版本。
  3. 理解新增需求：验证码放在哪一步、失败行为是什么、是否影响接口。缺少会明显改变方案的信息时再向用户确认，而不是假定所有细节。
  4. 基于现状修改：保留已有功能，补新逻辑和测试，同时运行原有登录测试，避免新功能破坏旧功能。

需要重新注入哪些信息

下一次模型请求至少需要当前新增要求、仍有效的项目约束、已有实现的简短说明、当前相关源码、已经做过的关键设计决定。若历史里有“为了兼容客户端不能改字段名”，这个原因也要保留。无需注入曾经失败的每一版补丁、所有编译日志或与登录无关的旧讨论。

可以把任务记录设计成几个明确字段：

原目标：实现登录
已完成：密码校验、会话生成；对应提交 abc123
当前新增：登录失败多次后要求验证码
仍有效限制：不改变旧客户端的成功响应字段
需重新检查：当前分支、接口实现、相关测试

这里的提交号只是示例。真实系统应记录实际版本，不能编造。

新要求和旧要求冲突怎么办

假如旧需求说“不增加验证码”，新需求明确要求增加，那么要把旧需求标记为被替代，而不是让两条要求同时作为有效规则进入模型。用户的“在原来基础上改”通常意味着其他不冲突的要求继续有效，但不能据此无限扩大修改范围。

实现时最容易漏掉的事

保存聊天不等于保存执行环境：临时容器可能已销毁，依赖版本可能不同。恢复时要验证环境；历史里记载“测试通过”，只说明某个版本在某个环境曾通过，不代表新版本也通过。

检验恢复能力可以做一次中断实验：完成一半后关闭程序，另一个人修改无关文件，再恢复追加功能。合格的实现应继续原任务、识别新需求、保留人工改动，并重新验证结果，而不是把旧快照无条件覆盖到现在。

哪些信息必须在压缩后继续保留？结合记忆分层说明保留规则。对于不能压缩或不能丢失的信息，你怎样在实现中落实这些约束？

问题来源：阿星不是程序员

必须保留的不是“所有看起来重要的聊天”，而是完成当前任务不可缺少、丢了就会改变行为的事实和限制。最重要的办法是把这些信息单独存成程序可检查的数据，不只让模型在摘要里自由发挥。

先区分四类材料

第一类是当前有效要求：用户要什么、明确不要什么、输出范围、成功条件。例如“只修改 sum.cpp，不改变接口”。这类内容应进入每次相关请求，并保留原文来源。

第二类是执行状态：哪些步骤完成、哪些工具调用已经执行、外部操作是否成功、还有什么待处理。例如“补丁已写入；测试超时；不能把它说成通过”。状态最好由实际工具结果更新，而不是从模型的总结猜出来。

第三类是支持结论的证据：具体日志、代码版本、文档页码。全文可以放在上下文外，但必须保留可重新读取的地址和版本。摘要说“测试失败”却找不到测试名和日志，后续很难继续排查。

第四类是暂时分析和旧材料：已经被否定的猜测、重复日志、过期源码。这些最适合缩短，必要时仍可从原始记录恢复。

与短期、长期记忆怎样配合

短期上下文负责本轮正在做的事；项目长期记录保存跨会话仍有效的约定；个人偏好记录保存用户明确的长期习惯。不要把“今天测试超时”写成永久项目事实，也不要让长期偏好覆盖用户本次明确要求。

长期记录进入本次上下文前要检查作用范围、更新时间和是否已被替代。保存得久不代表更权威。对于代码结构，当前仓库比一年前的笔记更可靠；对于权限，必须按当前配置判断，历史摘要中的“允许”不能自动恢复访问。

怎样落实“不能丢”

可以把输入拼装成三部分：受保护字段、可压缩历史、最新工具材料。压缩器只能处理第二部分；程序在压缩后比较受保护字段的标识和内容摘要，检查最新需求及未完成状态是否齐全。

protected: task_goal, active_constraints, pending_actions
compressible: old_discussion, superseded_outputs
references: source_id, path, revision, timestamp

上面是示意字段，不是某框架固定格式。若有一个尚未返回结果的工具调用，不能只保留请求却删掉它的对应关系。系统应该在安全边界压缩，或完整保留未完成调用的数据。

最后如何验证

准备几个很容易被摘要漏掉的条件：“不要删除文件”“必须兼容旧接口”“上次操作结果未知”。强制触发压缩，检查字段和后续行为。尤其测试否定词、用户后续纠正和跨会话过期信息。不能证明“模型永远不忘”，但可以让关键规则不依赖模型记忆，并通过程序测试发现退化。

延伸问题

如何管理持续膨胀的Checkpoint？

问题来源：TrustZone

Checkpoint 可以理解为任务执行过程中的“存档”，里面保存恢复任务所需的状态。它不是完整聊天记录的同义词，也不是所有长期知识的存放处。如果每一步都把越来越长的日志和文件全文重新存一份，存储量会迅速增长。

先算清楚增长来自哪里

假设每次存档包含 1 MB 状态，一次任务有 100 步，最简单的全量保存方式就可能需要约 100 MB。若状态本身每步继续追加，增长还会更明显。实际实现可能使用不同存储方式，不能直接套这个数字；例子的目的，是提醒先检查每份状态里放了什么。

哪些内容应该放到别处

恢复需要的任务编号、当前步骤、必要参数与结果引用适合保留。大型原始日志、截图和文档可以单独存储，在状态里保存受权限控制的引用与校验信息。但引用不能指向马上被清理的临时文件，否则存档存在却无法恢复。

长期记忆也应与任务存档区分：某个用户长期偏好不必在每一步重复复制，而某次任务尚未完成的工具调用也不能只写进模糊摘要。

删除要有明确规则

先确定保留目的：需要恢复最近未完成任务，还是需要审计某些历史操作？可以对不同状态采用不同保留周期，对完成任务做归档，对失败任务保留足够排查信息。具体删除接口和存储能力取决于框架及后端，不能假设一条通用命令能安全清掉所有旧记录。

删除某个旧存档之前，还应检查新存档是否依赖它、相关产物是否仍被引用、是否有审核任务尚未结束。法律或组织要求保留的记录也不能按普通缓存处理。

怎样判断优化成功

不仅看数据库变小，还要实际恢复一个保存过的任务，验证文件引用有效、权限仍正确、不会重复外部操作。持续记录每任务存档数量、平均大小和恢复失败率。如果只缩小存储却破坏恢复能力，就失去了 checkpoint 的主要目的。

大批日志怎样进入有限上下文？

问题来源：讨个offer咯

不能把几 GB 日志直接塞进模型输入。模型一次能处理的输入长度有限，而大量日志往往是重复信息。正确方向是先用程序定位与问题相关的证据，再把必要片段交给模型，并保留回到原始记录的办法。

先确定查什么

例如任务是“解释 10:05 到 10:10 的请求超时”，先限定服务、时间范围、请求编号和错误类型。按这些条件筛选，通常比先让模型总结全部日志更有效。若有 trace ID，可以把同一次请求经过的服务关联起来，但要留意不同机器的时间偏差。

保留有解释力的上下文

只提取包含 ERROR 的一行可能不够，错误之前的参数、重试和状态变化可能决定原因。可以保留错误前后固定范围，以及同一请求的相关事件。对大量重复消息记录出现次数和首末时间，不需要把每一份都发给模型。

但不能因为重复就删除少数特殊值。例如一千次普通超时里有一次权限错误，可能对应另一类问题。聚类或规则压缩之后，应保留异常类别和代表样本。

怎样让摘要能够核对

每个片段保留来源文件、时间范围和行号或事件编号。模型说“连接池耗尽”时，应指出对应证据；若只有大量超时而没有连接池状态，只能说这是一种待验证假设。

原始日志放在受控存储中，模型需要更多细节时通过查询工具获取，而不是最开始把所有内容都送入上下文。敏感字段应先按需要脱敏，不能为了调试把凭证和用户隐私完整暴露。

怎样验证没有压掉关键信息

选一些已知根因的故障，比较使用筛选片段后是否仍能发现根因。专门加入罕见错误、跨服务事件和时间边界样本。目标不是摘要越短越好，而是在输入预算内保留足够证据，并能在不确定时继续查原始记录。
