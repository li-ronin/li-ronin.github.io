1. 先把四个容易混淆的对象分开

设想一个修复程序的任务已经进行了两小时。磁盘上有 20 MB 日志，数据库里有 200 轮聊天，而下一次模型调用最多只能接收某个有限窗口。此时问“Agent 还记得多少”，其实混合了四个不同问题：系统保存了什么、这一次送进模型什么、任务进行到哪里、哪些知识应该跨任务保留。

原始记录是完整事件和证据，追求可追溯；上下文是当前一次推理的输入，追求此刻有效；任务状态是目标、限制、计划和执行结果的结构化表示，追求可恢复；长期记忆是未来任务仍有用的信息，追求正确召回。把它们全塞进一份不断增长的 messages 数组，初期简单，后期却会让压缩、恢复和纠错互相牵连。

可以类比 C++ 程序：磁盘文件不等于已加载到内存的对象，内存对象也不等于某个函数的局部变量。模型没有自动读取外部记录的能力；“存到了数据库”不代表它在下一次推理中可用。反过来，放进上下文一次，也不意味着模型参数永久学会了它。

下文的预算、状态字段与实验是一个可实现的教学设计，不是对某个商业产品内部实现的披露。LangGraph 的公开文档将线程状态 checkpoint 与跨线程 store 分开，提供了理解这两个作用范围的具体例子。参考：Persistence。

2. 用一笔预算理解为什么不能等到窗口满了再压缩

先采用一个教学假设：某模型的总上下文预算 C 为 32,000 tokens，且输入与输出共同占用这一预算。真实 API 可能另设最大输出限制或保留特殊开销，应以具体模型接口为准；这里不把 32K 当作任何产品的固定配置。令 I 为当前输入，R 为预期下一批工具结果，O 为输出预留，S 为安全余量，则必须检查 I + R + O + S ≤ C。

例如当前输入中：固定约束 1,500、目标和结构化状态 1,500、工具定义 2,000、最近对话 4,000、检索到的代码 6,000、旧日志 9,000，总计 I = 24,000。若下一步测试可能返回 4,000，输出预留 3,000，安全余量 2,000，则需求为 33,000，已经需要处理，虽然眼前输入仅占 75%。

这也解释了为什么“统一到 80% 才压缩”缺少依据。若工具返回大小波动很大，同一比例对小日志任务可能保守，对大构建任务却太迟。可以先给工具设置输出上限，再用历史轨迹的高分位结果长度估计 R；不要拿平均值覆盖最危险的长尾。计数器也必须使用匹配模型的 tokenizer 或服务端计数接口，字符数只是粗略代理。

预算不仅限制总量，还要限制结构。若 90% 空间被一份无关日志占用，即使请求能成功提交，也未必能正确决策。输入选择可以看成带依赖的背包问题：每项材料有代价、相关性和保留价值，但一个函数的定义与它的调用约束可能要一起选，不能简单按相似度逐句截取。

3. 把不能丢失的信息从自然语言摘要里拆出来

下面这个例子中，用户要求修复一个序列化错误，并明确“不要改变公开接口，不要提交远端”。如果摘要只剩“正在修复序列化问题，测试基本通过”，系统就丢掉了两条决定行为边界的约束，还把未验证的状态概括得过于乐观。压缩失败不一定表现为答非所问，也可能表现为程序继续工作，却执行了不该执行的操作。

一种更稳健的做法是维护受保护状态，压缩器只能产生叙述摘要，不能直接修改目标、授权和外部副作用结果。以下结构里的 evidence_ref 是可回查证据，base_revision 是代码版本；测试结果如果不绑定版本，代码修改后就可能被误当成仍有效。授权字段只是应用状态示意，真正执行时仍由独立权限检查作最终判断。

并不是所有事实都能由字符串相等保证。对来源证据里的语义条件，还需要人工或规则构造的测试；但把重要字段显式化，可以把“期望模型记住”变成“程序能检查是否丢失”。

{
  "goal": "修复序列化错误",
  "constraints": ["公开接口保持不变", "不推送远端"],
  "base_revision": "commit-A",
  "current_revision": "working-tree-B",
  "checks": [{"name": "unit", "revision": "A", "status": "passed"}],
  "open_issues": ["B 版本尚未运行回归"],
  "side_effects": [{"operation_id": "op-17", "status": "not_started"}],
  "evidence_refs": ["logs/run-17", "diff/A-to-B"]
}

4. 为什么可以分层压缩，而不是一次总结所有历史

“三层压缩”不是行业固定标准，更不是模型必须有三层记忆。分层的理由是不同对象允许的损失程度不同。下面从损失较小到损失较大的顺序给出一种设计，触发条件与阈值要通过任务实验调整。

第一层，整理原始输出。测试工具先保存完整日志，再只返回退出码、失败用例、关键堆栈和原文位置。移除重复编译进度不一定损失任务信息；但只保留最后 100 行就可能丢掉最早的根因。可让工具支持按错误类型、文件或行号再次查询，这样上下文不必承担日志仓库的职责。

第二层，按任务阶段形成摘要。一个失败假设已被证伪后，把十轮搜索变成“假设 H 已排除，证据 E，仍未验证条件 U”，保留最近正在操作的文件和关键工具调用关系。摘要应记录决策理由，而不只列操作流水。否则之后环境变化时，无法判断旧结论是否仍适用。

第三层，重建干净上下文。当历史过于碎片化或任务进入新阶段，从受保护状态、阶段摘要、必要原文和最近交互重新组装输入。旧历史仍保存在外部，不以删除记录换取窗口空间。若重新加载某个超大对象立即把窗口塞满，应该改变检索粒度，而不是不断“压缩—重载—再压缩”。

以刚才的 24,000-token 输入为例，若日志提炼后由 9,000 变为 1,500，输入降为 16,500；加上 R、O、S 为 25,500，预算就恢复了。这里节省的 7,500 并不是免费收益：我们必须验证失败用例、关键条件和证据位置仍可找回。

5. 把压缩当作一次有校验的状态迁移

一个容易忽略的细节是压缩器本身也会失败。它可能超时、返回无效 JSON、遗失约束，或者在压缩过程中原任务状态已经被新消息修改。因此不要直接执行 history = summarize(history)。更合理的顺序是：读取快照、生成候选、校验、确认快照仍是当前版本，再提交。

下面是语言无关的伪代码。版本比较体现乐观并发控制：候选摘要基于版本 12，但用户已发来改变需求的新消息，使状态来到版本 13，这时必须重新生成或做显式合并，不能把旧摘要覆盖回去。校验还应检查证据引用有效、未决问题没有被写成已解决。

对于工具调用，不能随意只保留一半协议。若历史里留下“工具返回”，却没有对应调用标识，某些 API 会拒绝输入；更隐蔽的情况是模型不知道该结果对应哪个对象。压缩必须按语义和协议的完整单元处理，不应把 token 截断器当成通用正确性机制。

snapshot = load_task_state()
candidate = summarize(snapshot.history, protected=snapshot.facts)

if not schema_valid(candidate):
    keep_old_context("invalid summary")
elif not evidence_refs_resolve(candidate):
    keep_old_context("broken evidence")
elif candidate.claims_done(snapshot.open_issues):
    require_review("unproved completion")
elif current_state_version() != snapshot.version:
    rebuild_from_latest_state()
else:
    atomic_commit(summary=candidate,
                  expected_version=snapshot.version,
                  preserve=snapshot.facts)

6. 如何发现压缩过度：测未来行为，不只测摘要好不好看

摘要很流畅，不意味着它足以支持后续任务。最有用的测试是保存同一个中间状态，构造两条后续轨迹：一条保留完整可用证据，一条使用压缩结果；给它们相同的后续要求，比较行为和产物，而不是只让另一个模型评价文字质量。

至少记录四类指标：关键约束保持率、相关事实召回率、任务成功率、单位成功任务的总成本。总成本应包含总结调用、重新读取证据和重复执行，而不只是压缩后一次调用便宜了多少。还可以统计“重复已经完成的动作”“使用过期测试结果”“反复询问用户已给的信息”等症状。

可以构造一个明确的反例：初始条件写明接口不能改变，中间混入 50 轮无关日志，压缩后要求增加一个可选字段。正确行为是兼容扩展；若系统修改了已有必需参数，说明约束保持失败。再加入一次用户变更“现在允许改变接口但需迁移指南”，检查系统是否能应用较新的指令，而不是把旧约束永久钉死。

恢复策略按损失程度选择：小范围缺证据就根据引用补读原文；发现摘要误述就回滚到前一版本并重压；发现状态已失真则从可靠 checkpoint 重建。对可能产生外部副作用的步骤，先核对真实结果，不能因为上下文忘了就重做。

7. 长期记忆不是把每轮对话再存一遍

上下文解决“这一次模型要看到什么”，长期记忆解决“什么值得在未来再次使用”。如果每轮都自动提炼五条记忆，几个月后很容易出现重复、矛盾和过时记录。写入记忆需要类似数据库更新的语义：新增、修正、失效和删除，而不只有追加。

一个记忆条目可以包含：主体、事实或偏好、来源、观测时间、适用范围、置信状态、有效期。例如“本项目使用 C++17”应绑定项目，不应传播成“用户所有项目只允许 C++17”；“这次希望简短回答”也不应该立即升级成永远简短。推断与明确陈述要分开。

写入前先判断未来效用、稳定性、可验证性和重复度。召回前先按用户与项目做隔离过滤，再按任务相关性选候选，最后检查时间和冲突。向量相似度只能表示某种语义接近，不能决定真伪与权限。对于“当前使用哪个版本”这样的信息，更新近且有直接证据的记录通常比历史总结更有用。

所谓静态长期记忆与动态长期记忆，可以理解为加载策略不同：少量稳定约定常驻，按任务需要的事实按需召回。不是必须再建两个数据库。给常驻部分设上限十分重要，因为每次请求都带上的内容会反复消耗预算。LangChain 文档讨论短期与长期记忆的作用范围；这里的准入、失效和冲突规则是面向可靠性的设计建议。参考：Memory overview。

8. 恢复会话、恢复文件、恢复外部世界是三回事

用户隔天说“在刚才的功能上再支持一种格式”，恢复聊天记录只是第一步。昨天的工作目录可能被修改，分支可能切换，依赖版本也可能更新。正确的恢复过程先读取任务状态，再读取当前文件与版本，最后核对外部资源，形成差异后重新规划。

例如旧状态记着“测试通过”，但今天仓库 HEAD 已变化。这条结果仍是有效历史，却不能证明当前版本正确。类似地，checkpoint 中记着“准备提交订单”，既不能证明订单已经提交，也不能证明可以重新提交。持久化需要保留状态，业务恢复还需要验证状态与现实是否一致。

Checkpoint 膨胀也不要靠随意清空解决。可为运行中的任务保留恢复必需快照，为关键里程碑保留审计快照，把巨大日志拆到对象存储，旧快照采用明确保留策略。清理前确保没有正在恢复的线程依赖它，引用过期应返回明确错误而不是默默变成空内容。

9. 怎样研究 Claude Code，而不把推断说成事实

截至本次资料核对，Claude Code 官方文档说明：接近窗口限制时会先清理较旧工具输出，必要时再总结对话，并提供 /context 与 /compact 等可观察入口。文档也提醒早期细节可能丢失，因此持久约定不能只依靠聊天历史。这里只陈述公开行为，不据此推断其内部一定采用本章的状态结构、打分函数或三层阈值。参考：How Claude Code works。

做源码级研究时，记录版本、入口函数、输入输出对象和调用链；闭源部分则记录实验条件与观察，明确标成黑盒推断。比如看见摘要保留最近文件，只能说明这次实验中出现了这一现象，不能证明所有版本都固定保留同样数量的文件。

一个可复查的实验记录应包含模型和客户端版本、原始任务、上下文统计、压缩触发时刻、压缩后要求与最终产物。不要用自己写的 Agent 伪代码替代产品证据，也不要拿营销中的“大窗口”作为无需压缩的证明。

10. 动手实验：先实现预算，再验证信息不丢

下面这段 Python 仅用于演示预算算术，不依赖模型、不自动调用任何外部服务。使用教学 token 计数，不冒充真实 tokenizer。保存运行后，断言会验证初始输入 24,000 对应总需求 33,000，以及日志提炼后总需求 25,500；最终打印 budget fits: True。它让触发规则可单元测试，而不是藏在一段自然语言提示里。

from dataclasses import dataclass

@dataclass(frozen=True)
class Budget:
    capacity: int
    next_tool: int
    output: int
    safety: int

    def need(self, parts):
        return sum(parts.values()) + self.next_tool + self.output + self.safety

b = Budget(32000, 4000, 3000, 2000)
parts = dict(rules=1500, state=1500, tools=2000,
             recent=4000, code=6000, logs=9000)
assert sum(parts.values()) == 24000
assert b.need(parts) == 33000
assert b.need(parts) > b.capacity
parts["logs"] = 1500
assert b.need(parts) == 25500
print("budget fits:", b.need(parts) <= b.capacity)
  1. 将规则提取为独立函数，为零预算、超大工具返回、摘要失败和新消息到达建立测试。
  2. 构造十个带约束的短任务，手工写出必须保留的事实与证据。先用人工摘要验证状态结构，再接入模型摘要，避免把数据建模问题误当成模型能力问题。
  3. 分别测试“只截断”“只摘要”“受保护状态＋摘要＋补读”，比较成功率、证据回读次数与总 token 消耗。实验结果可能随任务变化，不预设复杂方案必然优胜。
  4. 当你能够解释一条具体约束从用户输入、持久状态、压缩到执行检查的完整路径时，才算真正理解了“保留关键信息”，而不是只会复述这个词。
