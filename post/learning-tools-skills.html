工具、Skill 与 MCP：能力怎样接入，流程怎样复用

1. 不要把三种不同层次的东西互相替代

工具回答“宿主程序能做什么”，例如读取文件、执行测试、查询订单；Skill 回答“面对某类任务，怎样组织这些能力更可靠”；MCP 回答“应用与外部能力提供者怎样用共同协议连接”。三者有交集，但不是同一种抽象。

以 C++ 类比：工具像有明确接口的函数，Skill 更像可按需加载的操作规程和示例集合，协议像让不同组件交换请求与结果的约定。这个类比不是精确类型关系，只是帮助建立直觉。一个 Skill 可以指导模型调用工具，却不能凭一份说明文件获得操作系统执行权限。一个 MCP server 也不会因为实现协议就天然可信。

本文案例是“为序列化器的空数组行为补回归测试”。先找到实现与测试框架，再复现故障、修改代码、运行测试、检查差异。工具提供读写与执行能力，Skill 规定回归测试优先的步骤，运行时保管目标、预算和权限。

2. 一次工具调用到底发生了什么

运行时先把工具描述和参数 schema 提供给模型。模型返回结构化请求，比如 read_file(path="src/serializer.cpp")。宿主程序解析请求，校验参数与权限，真正读取文件，再把带有调用关联标识的结果送回模型。模型随后依据结果决定继续调用或生成回答。服务端托管工具可能由提供方执行，不能将这种客户端模式套到所有产品。参考：Tool use。

在教学轨迹里，第一次模型调用提出 read_file；宿主执行一次工具；第二次模型调用提出 run_tests；执行一次工具；第三次模型调用解释结果并结束。因此是三次模型请求、两次工具执行。若第二次模型响应提出两个可并行的工具请求，工具执行次数增加，但这轮模型请求仍只有一次。流式返回被分成多个网络片段，也不等于多次推理请求。

“Skill 用了几次”则必须先定义指标：被发现、被载入、步骤被执行，是不同事件。技能文本放进上下文不必然触发额外模型调用，读取技能文件可以由宿主直接完成；某些实现选择让模型调用读取工具，才会增加相应调用。不能把工具次数、技能次数和模型次数写成固定等式。

3. 好工具首先是好接口，不是漂亮描述

对于 run_tests，参数应表达业务意图而不是提供无限制命令字符串。例如 suite 只能选择 unit 或 serializer，timeout_seconds 有范围限制，工作区由宿主确定。这样既便于模型选择，也减少歧义与越权面。schema 正确仍不代表操作安全：一个字符串格式合法的路径，也可能指向工作区以外。

以下为宿主侧伪代码。接口声明解决“输入长什么样”；业务校验解决“这次输入可不可以”；沙箱与操作系统隔离解决“即使程序出错，最坏影响是什么”。三层不应互相替代。实际路径安全还需要处理符号链接、竞态和挂载边界，简单字符串前缀判断不足以保证隔离。

def run_tests(args, context):
    validate_schema(args, TEST_SCHEMA)
    if args["suite"] not in {"unit", "serializer"}:
        return error("unsupported_suite")
    authorize(context.identity, "run_tests", context.workspace)
    command = PREDEFINED_COMMANDS[args["suite"]]
    result = sandbox.run(
        command, cwd=context.workspace,
        timeout=min(args["timeout_seconds"], 60),
        network=False
    )
    return {
        "status": classify(result),
        "revision": workspace_digest(),
        "failed_tests": parse_failures(result),
        "log_ref": evidence_store.put(result.full_log)
    }

4. 工具结果要帮助决策，而不是倾倒输出

一个有用的测试结果包含运行是否真正开始、退出状态、失败用例、代码版本、日志引用和截断说明。若超时后子进程仍在后台运行，也要说明，不能仅返回“失败”。如果只给模型一句“测试失败”，它无法区分编译错误、环境缺依赖、断言不满足或工具自身异常。

对大日志返回摘要与引用，而不是无限量正文；但不能把“输出截断”悄悄变成“没有其他错误”。对不可信网页、文档和日志中的命令，不应因为它们出现在工具结果里就提升为新的用户指令。数据的来源和可用性，与它是否有资格改变权限，是两回事。

5. Skill 的核心是可发现、可执行、可验证

Agent Skills 规范使用含 SKILL.md 的目录组织技能，并支持附带脚本、参考资料和资源。发现阶段可先提供名称和描述，选中后再加载主体或资源，这种渐进加载避免每轮塞入全部说明。这里仅概述公开规范，不意味着所有客户端都实现相同加载策略。参考：Agent Skills specification。

一个好的“补回归测试”技能应说明适用条件、所需输入、执行步骤、证据要求、失败处理和完成标准。例如先记录复现命令与失败输出，再修改实现，之后运行定向测试和相关回归；不能把“测试没跑成”写成“测试通过”。技能若只有“请认真修复代码”，没有增加可执行知识。

分层应服务于维护边界：通用层规定证据和安全原则，领域层解释 C++ 测试习惯，仓库层给出该项目的构建命令。重复规则需要明确优先关系，避免三个技能对同一文件产生互相矛盾的要求。不要为了分层形式把十行内容拆成八份难以追踪的文件。

6. 匹配技能是一项检索与决策任务

最简单的匹配是由规则选择，例如收到“运行回归测试”时选择测试技能；当任务表达多样，再考虑关键词、语义检索或模型分类。候选阶段追求不要漏掉合适技能，选择阶段检查适用条件、输入是否齐全和冲突。只凭名称相似就加载，会把“性能测试”与“单元测试”混在一起。

可以构造一个小评测集：真正需要该技能的任务、不需要它的相似任务，以及需要两个技能协作的任务。统计正确选择率、误触发率、加载 token 和最终任务成功率。高召回却总把十个技能一起塞入上下文，可能只是把选择负担转嫁给模型。

技能沉淀也不应等于自动把每次成功轨迹变成通用规则。先提取候选流程，删除凭据和一次性路径，标明适用范围，在不同输入上回放验证，再版本化发布。一次偶然成功不足以证明可复用；失败案例和停止条件往往比“最佳实践”口号更有价值。

7. MCP 与 RAG 分别补上哪里

MCP 的架构包括宿主应用、客户端与服务器；宿主管理连接与应用行为，客户端与服务器进行协议交互。协议减少的是每个应用重复设计工具发现和消息格式的成本，不会消除工具自身的业务实现、认证、权限和错误语义。参考：MCP 架构。

RAG 则主要解决“当前需要哪些外部知识”。若知识量大、经常更新、必须引用来源，检索通常比把全文写进 Skill 更合理；若内容是稳定步骤、判断规则或质量标准，Skill 更适合。二者常常组合：技能告诉 Agent 如何回答某类问题，工具执行检索，检索返回最新事实，回答附证据。

例如诊断接口超时：Skill 描述先看时间范围、再检查依赖、禁止未经授权重启；RAG 取回当前服务文档和历史事故；监控工具提供实时指标。文档不是实时状态，技能不是执行权限，MCP 也不是推理算法。把这些边界讲清楚，系统才不容易把过期知识当成事实。

8. 用一个小实验检验分层是否有价值

为同一个修复任务做三套配置：只有工具；工具加清晰的测试 Skill；工具加冗长但无操作细节的 Skill。保持模型和预算一致，记录能否复现、是否验证、是否错误声明成功，以及工具和模型调用次数。不要预设“加了技能一定更好”。

  1. 故意让工具返回无效参数、超时、截断日志和不可信指令，检查宿主是否能保留正确边界。
  2. 为技能路由准备至少十个正例、十个相似负例；记录误匹配原因，改描述后重新评估旧用例，防止修一个任务破坏另一个。
  3. 画出工具提供者改变时哪些代码需要改。若替换 MCP server 后业务规则全部重写，可能是适配层与业务层耦合过深。
  4. 总结你自己的 Skill 时，给出一个实际失败前后对比和版本差异。没有这份证据，就把结论写成待验证的设计假设，而不是虚构经验。
