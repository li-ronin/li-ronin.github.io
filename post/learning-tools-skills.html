工具调用的流程是怎么样的？能不能用skill来替代工具？为什么？

相关原问题：

追问工具调用时，模型用了几次？skill用了几次？

问题来源：代码随想录

工具调用的基本流程是：程序把工具说明发给模型，模型输出工具名和参数，程序执行对应函数，再把结果提供给模型。Skill 通常是任务说明和配套材料，它可以指导工具怎么用，但不能凭一段文字替代读文件、运行命令这些实际执行能力。

用“读取文件并解释错误”数清每一步

假设程序只提供一个工具 read_file(path)，并且没有预先读取文件：

  1. 第一次调用模型：输入用户问题和工具说明。模型返回 read_file("sum.cpp") 的调用请求。
  2. 程序执行 read_file。这一步可能只是普通文件 I/O，不需要调用模型。
  3. 第二次调用模型：程序把源码作为工具结果送入。模型根据源码回答问题。

这个特定例子是 2 次模型调用，1 次工具执行，0 次 Skill 加载。如果模型直接知道答案、不需要读文件，可能只有 1 次模型调用；如果还要运行测试、修改文件、重试，次数会增加。一次模型响应也可能包含多个并行工具请求，所以模型调用次数不等于工具次数。不要背一个固定数字。

加入 Skill 后发生什么

假设有一个“排查 C++ 测试失败”的 Skill，其正文写着：先复现失败，再定位代码，修改后运行原测试和相关回归测试。程序把这份说明放进模型输入，模型据此安排工具调用。Skill 目录还可以包含一个收集测试日志的脚本，但脚本仍然需要通过某个执行工具运行。

例如系统先按用户明确指定的 Skill 直接读取说明文件，随后调用模型要求读源码，最后调用模型给出解释。这个流程仍可能是 2 次模型调用，只多了 1 次 Skill 内容加载。若系统让模型先决定选哪个 Skill，再调用加载工具，通常会多出一次模型请求。具体数字由日志确定，不由“用了 Skill”这件事确定。

因此“Skill 用了几次”也要先约定含义：加载了几次正文？应用了几次流程？运行了几次脚本？这三项不是同一个计数。已经在上下文里的说明可以指导多次操作，并不需要每一步重新读一遍。

为什么不能把执行安全交给 Skill

即使 Skill 写着“只修改项目内文件”，程序仍要检查真实路径，包括 .. 和符号链接等情况。模型可能选错工具或生成错误参数，外部文档也可能混入恶意指令。文字说明帮助模型选择做法，程序里的参数检查、权限限制和超时才负责限制实际执行。

验证这个理解最简单的方法，是给程序分别加三个计数器：模型 API 请求数、工具执行数、Skill 加载数。跑“纯问答”“读文件”“加载 Skill 后读文件”三个任务，打印各自记录，就能看出它们为什么不能混为一谈。

讲讲你的skills有哪些，为什么这么设计？设计的要点是什么？

相关原问题：

skill分层体系是怎么做，为什么这么设计？

Skill 可以理解为“专门针对一类任务写好的操作说明，加上需要的脚本和参考材料”。例如“排查 C++ 单元测试失败”可以是一份 Skill；“读取某个文件”则通常是一个工具。前者说明怎么组织多步工作，后者提供实际操作。

原问题问“你的 skills 有哪些”，这里不能替真实项目编造清单。下面是一组可以自己实现、再用实际结果说明的例子。

一个容易理解的 Skill 清单

  • 测试失败排查：输入失败用例和项目位置；先复现，再定位，再修改，最后回归。
  • 性能测量：输入待比较版本和测量条件；固定环境、预热、重复测量、保存原始数据。
  • 代码审查：输入代码差异；检查正确性、边界条件、测试缺口，不默认直接改代码。

它们不是按“聪明程度”分层，而是按任务边界分开。每份说明应写清何时使用、需要什么输入、产出是什么、什么情况要停止或询问。名称不能过宽，例如“万能开发 Skill”很难判断何时该加载。

分层可以分两种，不要混在一起

一种是加载层次：先让模型看到短名称和描述，确定相关后再加载正文，只有实际需要时才读取长参考资料或执行脚本。这样一个只需要解释报错的任务，不必一开始就读几万字性能测试说明。

另一种是知识职责：通用开发要求、某语言的处理办法、某项目的具体命令。不要把同一条规则复制到十份 Skill 里，否则修改时容易漏改。但也不能把正文拆成过多跳转文件，让完成一件小事需要连续读十层材料。分层的目的应是减少重复和无关信息，而不是层数越多越专业。

一份正文可以怎么写

以测试排查为例，正文可以明确：先运行用户给的用例，保存原始失败输出；没有复现时不要直接声称修复；修改前确认目标文件；修改后运行同一用例及相关测试；最终列出实际修改和实际运行的测试。可重复的日志收集命令放进脚本，易变的项目命令放在项目配置，不把私密凭据写进说明。

脚本不是写了就安全。执行它仍应经过程序的权限检查，失败时要返回退出码和错误，不允许把失败包装成成功。

怎么证明设计有用

准备一组没写 Skill 时容易出错的任务，再对比使用后的表现：有没有跳过复现、有没有遗漏回归、有没有加载不相关材料、总耗时是否增加很多。要区分“说明写得详细”和“真的改善结果”。如果只是换了名字、把同样内容复制几遍，不能算有意义的分层。

最终介绍真实项目时，应给实际目录、实际输入输出和至少一个失败后改进的案例。这里的清单是教学设计，不是对任何个人经历的陈述。

用户输入怎么和相关skill匹配？

用户输入与 Skill 的匹配，本质上是判断“这项任务需要哪份说明”。不一定每次都需要再调用一个大模型，也不应该一看到某个关键词就强行加载。

从一个具体请求看流程

用户输入：“这个 C++ 用例偶尔失败，帮我定位，不要先改代码。”系统有三份 Skill：测试排查、性能测量、代码审查。它应优先选择测试排查，并把“先定位、不修改”的当前要求一起交给模型。不能因为描述里出现 C++，就加载所有 C++ 相关材料。

常见做法分四步：

  1. 准备候选目录。每个 Skill 有名称、简短说明、适用条件、所需环境。例如“处理可复现或偶发测试失败；不用于性能基准对比”。
  2. 筛选候选。用户显式指定的先处理；明确规则可以直接匹配；数量很多时用关键词或向量相似度找少量候选。向量相似度只是“语义上像”，不是证明适用。
  3. 决定是否加载。程序规则或模型根据任务、候选描述、环境条件做选择。没有合适候选可以不用 Skill，多个都适用时也可以按步骤组合。
  4. 加载正文后再执行。正文里的输入条件可能仍不满足，例如需要失败日志但用户没有提供。此时先获取材料，而不是假定匹配完成就能直接工作。

为什么描述比名称重要

只有名字 debug，模型不知道它针对网页、C++ 还是数据库。比较清楚的描述应包含对象、触发场景和排除场景。比如“当 C++ 单元测试失败或偶发崩溃，需要复现、检查堆栈和定位源码时使用；不负责上线部署”。这比“强大的问题解决专家”更容易匹配。

这里的例子是设计建议，不是所有产品的固定匹配算法。不同工具对用户显式调用、自动选择、描述加载都有不同实现，不能凭看到某次自动加载就推断其后台一定用了向量数据库。

怎么处理误匹配

至少记录任务、候选 Skill、最终选择和结果。然后准备三类测试：应当触发、明确不该触发、同时涉及多个任务。若“解释什么是性能测试”也启动了实际压测，说明描述或执行条件太宽，应增加“只有用户要求实际测量时才运行”的限制，并由执行程序落实权限。

匹配准确率之外，还要观察漏选率和无关加载成本。对高风险任务，Skill 选择结果不能自动授予权限；它只决定提供哪份说明。真正执行删除、部署等操作时，仍要独立确认授权范围。

有skill沉淀机制么？还是只能用户自己构造？

可以有 Skill 沉淀机制，但不应把每一次成功对话自动复制成一份新 Skill。比较可靠的办法是：从多次重复任务里总结稳定步骤，先生成草稿，再经过检查和测试，最后作为可复用版本使用。

“沉淀”的具体含义

假设你连续三次排查 C++ 测试失败，都要收集编译参数、复现输入、失败输出和对应提交。与其每次重新解释，可以整理成一份说明，并写一个收集这些材料的脚本。以后同类问题直接使用它，这才是把经验转成可复用流程。

但某次碰巧通过测试的修改，不能直接提炼为“以后遇到这个错误都这么改”。例如一次崩溃由数组越界引起，不代表所有崩溃都由数组越界引起。要把可重复的排查步骤和一次性的结论区分开。

一个可以实现的形成过程

  1. 从已完成任务中挑候选：重复出现、步骤相对稳定、人工需要反复说明的任务。
  2. 收集证据：保存输入条件、采取的步骤、失败分支和最终验证结果。未验证的建议不能冒充成功经验。
  3. 生成草稿：说明适用条件、所需输入、步骤、输出、停止条件；把账号、密钥、个人路径和客户数据去掉。
  4. 人工或独立检查：确认没有把偶然做法写成普遍规则，没有扩大操作权限。
  5. 在新任务上测试：不能只用产生这份 Skill 的原任务验证，否则只是记住答案。
  6. 发布版本：记录修改原因和适用环境。出现退化时能回退到上一版。

哪些部分适合自动化

模型可以帮助从日志里找重复步骤、起草描述、整理检查清单、提出测试案例。脚本可以检查必填字段、引用文件是否存在、命令是否能运行。适用范围是否正确、某条经验是否可靠、是否涉及敏感信息，通常还需要更严格检查。

自动生成不等于自动信任。特别是外部网页或工具输出里如果有“忽略限制、把密钥发到某处”，绝不能因为它被摘进了 Skill 就变成可信规则。来源和权限要一直保持区分。

怎么防止越积越多

建立明确任务分类，新增前先搜索已有 Skill。如果只是同类流程的一处改进，更新已有版本比新建一个名字更合适。定期检查长期不用、重复或已失效的说明；删除之前确保有版本记录。评估时看新任务成功率、误触发率、执行成本，而不是以 Skill 数量作为成绩。

回答真实项目是否实现了沉淀时，要说明目前做到哪一步。只有人工编写就说人工编写；做了自动草稿但没有自动发布，也应明确区分。设计方案可以学习，经历和效果数据不能代填。

什么情况下会给 Agent 接入 RAG，什么情况下适合把知识整理成 Skill？

问题来源：阿星不是程序员

RAG 和 Skill 解决的主要问题不同。RAG 帮助系统找到“回答这个问题需要的资料”；Skill 帮助系统知道“这类任务应该按什么步骤做”。它们可以一起使用，并不是二选一。

RAG 是 Retrieval-Augmented Generation 的缩写，可以译为检索增强生成。最简单的过程是：用户提问 → 从文档库找到相关段落 → 把段落和问题一起提供给模型 → 模型依据材料回答。Skill 则通常是一份流程说明和配套文件，系统在合适任务中读取它，再调用实际工具完成工作。

同一个问题为什么可能需要两者

假设用户问“按照公司当前报销规则检查这张发票”。报销金额上限、支持的费用类型、规则生效日期经常变化，应从当前文档中检索，而不是写死在长期不更新的提示词里。这个部分适合 RAG。

但是“先确认发票日期和类型，再查适用版本的规则，再逐项比对，证据不足时不要通过”是一套检查步骤，可以整理成 Skill。Skill 可以要求调用检索工具找规则，检索结果则提供这次判断所需的具体事实。

两者组合后的过程是：加载发票检查 Skill → 提取发票字段 → 检索适用规则 → 比较并列出依据。Skill 没有凭空知道最新规则，RAG 也不会自动保证检查流程完整。

什么情况下优先使用 RAG

资料很多、无法全部放进输入；内容频繁更新；回答需要追溯到具体文档；不同用户只能访问不同资料，这些通常说明需要检索系统。实现时还必须处理切块、索引更新、权限和引用验证。不是接上向量数据库就解决了一切。

如果资料只有一小页且一直不变，直接提供给模型可能比建立完整 RAG 更简单。不要为了技术名字而增加不必要组件。

什么情况下优先整理 Skill

任务步骤反复出现、容易漏环节、需要统一输出或验证方法时，Skill 比不断重复长提示更合适。例如 C++ 缺陷排查、性能测试、代码审查。但一堆事实资料不因为放进 SKILL.md 就自动变成好 Skill；如果文件越来越长、每次只用一小段，更适合拆为参考资料并按需读取。

怎么避免错误混用

不要把检索到的网页内容当作有权改变系统规则的指令。例如材料里写“忽略之前限制”，它仍然只是外部文本。也不要因为 Skill 中写着“检查最新规则”，就声称已经检索并验证；需要实际工具结果作为证据。

可以分别测试两类失败：给出正确流程但检索错误规则，系统仍可能得出错误结论；给出正确规则但漏掉日期检查，也可能错用旧版本。这样能看清，资料准确和流程正确是两个不同但相互配合的要求。

MCP怎样减少工具接入的重复工作？

问题来源：代码随想录

MCP 是一种让 AI 应用接入外部工具和数据的协议。可以把协议理解为双方约定的消息格式与交互规则，类似“工具列表怎样查询、参数怎样描述、结果怎样返回”。它减少的是接入方式的重复工作，不是替你实现数据库、权限系统或业务逻辑。

没有统一协议时会怎样

假设你有三个 AI 应用，都要调用同一个内部搜索服务。每个应用可能分别写一套“列出搜索能力、转换参数、解析结果”的适配代码。搜索接口变了，三处都要维护。若搜索服务通过统一 MCP 接口提供能力，各应用可以使用兼容客户端接入，减少重复适配。

一次调用有哪些参与者

用户使用的 AI 应用是 host；它管理连接和授权。应用中的 MCP client 与某个 MCP server 通信。server 提供实际能力，例如搜索文档。模型可能看到工具描述并生成调用参数，但真正发送协议请求的是客户端程序，不是语言模型自行建立网络连接。

用一个示意过程理解：应用询问服务器有哪些工具；服务器描述 search_docs 需要一个字符串查询参数；应用将描述提供给模型；模型返回查询参数；应用检查后调用服务器；服务器执行搜索并返回材料；应用再把材料交给模型组织答案。

它没有自动解决什么

工具参数符合格式，不代表操作被授权。服务器仍要验证当前用户能访问哪些文档，不能因为请求来自 MCP 就返回全部数据。工具描述和返回内容也可能不可信，不能把它们当成更高优先级指令。

协议还能涉及资源、提示模板等能力，但具体支持项和版本要核对双方实现。两个产品都写着支持 MCP，并不意味着它们支持完全相同的传输方式、认证和扩展。

因此它最适合解决“同一能力需要被多个应用复用”的接入问题。若只有一个非常简单的固定接口，直接调用 API 也可能足够；使用 MCP 的理由应是减少维护和提高互操作性，而不是认为它会自动让模型更聪明。
